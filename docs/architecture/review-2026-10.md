# Architecture Review 2026-10 (roadmap step 19)

Story 19.1. Author: Winston (architect). Date: 2026-10-11. Code at `642ba5e` (after black, story 5.3).
Read-only review: nothing in the code was changed. Every finding has a command to reproduce it.
Helper scripts (not committed) are described in [Evidence commands](#evidence-commands).

Summary:
- **Second pass (section 5) found three high-severity bugs in live trading paths. Fix them before the refactor:**
  - **F19:** a signal from channel B is silently skipped when channel A once had a signal with the same message id.
    Replies can also be linked to the wrong channel's trade.
  - **F20:** a valid French signal ("Je vends gold 4150 SL… TP…") posted within 5 min of an open trade in the same
    chat is taken as a follow-up and never executed. Reproduced with a script.
  - **F21:** break-even is marked done before it is applied. If the SL move fails, it is never retried.
- `main.py` (1,836 lines, 42 methods + 2 functions) holds seven concerns. Split it into five
  modules under a new `src/app/` package. `main.py` then keeps only wiring and lifecycle (~350 lines).
- About **2,400 lines of production code never run**: five modules that nothing imports
  (`break_even`, `position_modifier`, `close_processor`, `context_processor`, `symbol_specs`) and two
  empty packages. The live code does break-even, close and modify inline in `main.py`.
- The four suspected dependencies (`aiofiles`, `apscheduler`, `pendulum`, `aiohttp`) are **not imported
  anywhere**. Remove them.
- The console **STOP ALL** command can never be typed and would not block orders anyway (F3). The duplicated
  logic around levels and metadata (F7–F9) will make steps 3, 4, 13 and 18 change several places.
- Plan: fix stories first (roadmap step 20, section 5.3), then 8 refactor stories (19.2–19.9): characterization
  tests first, then one extraction per story.

### Duplicated logic

**F7 (M) – Telegram message → `metadata` dict is built in three places.** `message_handler.py:115–128`
(push), `message_handler.py:135–146` (error fallback), `main.py:1531–1544` (polling, with its own sender
rule `user_<id>`/`channel_<id>` that differs from `_get_sender_info`). An edit made to one (e.g. step 18
channel filtering, or a new field for step 13 edits) can miss the others.
Action: simplify. One `message_metadata(message, chat_title)` function in `message_handler.py`, used by both paths.

**F8 (M) – "Naive UTC timestamp + message object from metadata" is built twice in `main.py`.**
main.py:337–347 (`CorrelationMessage`) and main.py:468–481 (`ContextMessage`). Same fields, same tz fix.
Action: simplify (one helper in the router).

**F9 (M) – `PositionManager` is created lazily in three places.** main.py:562, 1227, 1393
(`self.position_manager = self.position_manager or PositionManager(...)`). `_track_setup_legs` and
`_check_close_invalidation` silently do nothing while it is still `None`. Action: simplify. Create it once
in `_initialize_mt5_connection`, right after the connection.

**F10 (L) – Dashboard stats update is written twice** in `_on_telegram_message` (main.py:353–361 and 430–437).
Action: simplify (one `finally`-style call at the end of routing).

**F11 (L) – `normalize_price(..., "GOLD")` is hard-coded** in `position_manager.py:677, 687` (and in dead
modules). The live paths at 233, 236, 519 use `position.symbol`. Only `validate_modification_success` (dead, F6)
uses the hard-coded symbol. Action: goes away with F6.

### Other findings

**F12 (M) – Fire-and-forget task without a reference.** main.py:608
`asyncio.create_task(self._apply_setup_levels(setup, rearm_changes))` keeps no reference. Python docs:
such a task can be garbage-collected before it finishes, and its exceptions are never logged. This is an SL/TP
change on live positions. Action: simplify. Keep the task in `_component_tasks` (or await it) when moving `_start_setup`.

**F13 (L) – Dedupe set trimming keeps random keys, not recent ones.** main.py:269–271
`set(list(self._seen_message_keys)[-2500:])`: a `set` has no order, so "last 2,500" is arbitrary. A recent key
can be dropped and its message processed twice (the signal-claim in the database still blocks a second order
for the same message id). Action: simplify. Use a `dict` (insertion-ordered) or `collections.deque` + set.

**F14 (L) – `@retry_on_failure` on `open_market_order` and `close_position_full` never fires.** The
bodies catch every exception and return `MT5Result(success=False)` (e.g. position_manager.py:447–454), so the
decorator never sees one. It is harmless today, but it would become dangerous: if someone removes the
`except`, a timeout after a filled order would **send the order again**. Action: simplify. Remove
`retry_on_failure` from order-sending methods (open, close); keep it only on reads.

**F15 (L) – `mt5.order_send` is a blocking call inside async code** (position_manager.py:401). The event
loop stalls for the order round-trip, usually tens of ms. Keep for now (reason: one order at a time is fine
at this volume). Revisit if steps 16/17 run several brokers in one process (they don't: one process per broker).

**F16 (L) – The "connection pool" is one session copied N times into a queue.** connection.py:396–417:
`connection_queue` holds `max_connections` references to the same `MT5Connection`. Equivalent to an
`asyncio.Semaphore(N)` around one session. Action: keep for now (high-risk MT5 code, works). Simplify only
if `connection.py` is opened for another reason.

**F17 (L) – `main.py` calls a private method** `mt5_connection_manager._ensure_initialized()` (main.py:1573).
Action: simplify. Rename to a public `initialize()` when the wiring moves.

**F18 (M) – Telegram polling does not go through the rate limiter.** `_poll_telegram_groups` calls
`client.get_messages` per group every 3 s (main.py:1499–1505) with no `human_delay()`. The coding standard says
every Telegram call goes through `rate_limiter.human_delay()`. Reads at this rate have run fine so far.
Action: keep the behaviour, but when the poller moves (story 19.4), route its calls through the existing
`telegram_client/rate_limiter.py` or record the deliberate exception in `coding-standards.md`.

## 3. Target structure

New package `src/app/` holds the orchestration that is in `main.py` today. Classes get their
collaborators in the constructor. There is no new framework, no event bus and no interfaces.
Background tasks go through one `spawn(name, coro)` callable that the wiring owns, which fixes F12 for free.

```
main.py                          ~350  wiring + lifecycle only (A)
src/app/__init__.py                 0
src/app/router.py                ~230  MessageRouter (C) + correlated follow-ups (D)
src/app/zones.py                 ~300  ZoneWatcher (E)
src/app/setups.py                ~420  SetupRunner (F)
src/app/execution.py             ~280  OrderExecutor (G)
src/telegram_client/poller.py    ~100  poll_groups() (B), uses message_handler.message_metadata (F7)
```

| Target | Receives from `main.py` | Holds |
|--------|-------------------------|-------|
| `main.py` | `__init__`, `startup`, all `_initialize_*`, `run`, `shutdown`, `_save_application_state` (trimmed, F4/F5), `_shutdown_monitoring_components`, `_cancel_component_tasks`, `_shutdown_logging`, `signal_shutdown`, `signal_handler`, `main` | Builds every object, owns `_component_tasks` and `spawn`, attaches MT5 when its background init finishes |
| `src/app/execution.py` `OrderExecutor` | `_validate_live_price`, `_order_volume`, `_risk_guard_refusal`, `_handle_parsed_signal`, `_execute_signal_on_mt5`, `_apply_position_levels` | `mt5` (connection manager), `position_manager` (created once on `attach_mt5()`, F9), signal + position repositories, dashboard |
| `src/app/setups.py` `SetupRunner` | `_start_setup`, `_apply_setup_levels`, `_disarm_or_drop`, `_handle_setup_edit`, `_handle_setup_followup`, `_llm_setup_followup`, `_watch_setup`, `_check_close_invalidation`, `_maybe_fire_setup`, `_fire_next_leg`, `_track_setup_legs` | `SetupAggregator`, `OrderExecutor`, `regex_parser`, `llm_parser`, `spawn` |
| `src/app/zones.py` `ZoneWatcher` | `_start_zone_watch`, `_apply_zone_followup`, `_watch_zone`, `_advance_zones`, `_zone_setup`, `_author_zone_sl`, `_zone_now_leg`, `_on_zone_confirmed` | `SetupAggregator`, `SetupRunner` (starts the setup watcher, applies levels), `OrderExecutor.mt5` for candles/price, `spawn` |
| `src/app/router.py` `MessageRouter` | `_on_telegram_message`, `_handle_correlated_message` | dedupe keys (F13), counters, `ZoneWatcher`, `SetupRunner`, `OrderExecutor`, `CorrelationEngine`, parsers, dashboard |
| `src/telegram_client/poller.py` | `_poll_telegram_groups` | Telethon client, group entities, callback = `router.on_message` |

Each file stays under ~450 lines; `main.py` is wiring only. `SetupAggregator` stays where it is
(`correlation_engine/setup_aggregator.py`, pure state, 503 lines, well tested).

Dependency direction (no cycles): `router → zones → setups → execution → mt5_executor / database`.
`zones` needs `setups` (a confirmed zone becomes a setup). `setups` never imports `zones`. The one
backward look today (`_watch_setup` reads `get_zone(...).linked_setup`, main.py:1036–1039) uses the
shared `SetupAggregator`, not the zone module.

### Seams for the next roadmap steps

- **Step 18 (channels per broker):** groups come from `settings.get_telegram_groups()` →
  `telegram_client/client.py:227` → connected entities → both the push handler and `poller.py`. After the split,
  one setting change still reaches every path. The only `main.py` code involved (`_poll_telegram_groups`)
  moves into `telegram_client/poller.py`.
- **Step 3 (persist state):** all in-memory trading state (setups, zone watches, legs, `be_done`) lives in
  `SetupAggregator`, and the watchers are started only by `SetupRunner.start_watch()` / `ZoneWatcher.start_watch()`.
  Restore = load from the repository → `aggregator.adopt()` / `start_zone()` → call those two methods. No change in router or execution.
- **Step 4 (alerts):** the events to alert on all happen in `execution.py` (fill, reject, risk guard),
  `setups.py` (break-even, invalidation, watcher error) and `zones.py` (phase change). Pass an `alerts` object to
  those three constructors.
- **Step 16 (control page):** reads state from `SetupAggregator` and the database; kill switch = `data/STOP_TRADING`
  (F3). No dependency on `main.py`.

## 5. Second pass: correctness of the live paths

The first pass looked at structure. This pass reads the paths that touch money line by line: message routing →
correlation → parse → setup/zone → sizing → risk guard → order → break-even / invalidation → persistence. It
also covers the MT5 connection lifecycle, Telegram ingest and `cli.py`. Each claim was checked in the code.
F20 was also reproduced with a script.

### 5.1 High severity

**F19 (H) – Signals are keyed by Telegram message id alone, but message ids are per channel.**
`models.py:125-126`: `telegram_message_id` is `unique=True` across all chats. Every lookup ignores the chat:
`SignalRepository.find_by_message_id` (repository.py:318-324), `save_signal` (repository.py:288-296, returns the
existing row), execution (main.py:1376), the edit check (main.py:321) and the reply-chain lookup
(`correlator.get_position_by_message_id`, correlator.py:350). In channels and supergroups each chat has its
own message counter, so two channels reach the same ids.
Failure 1: channel B posts a complete signal whose id equals any signal channel A ever stored → `save_signal`
returns A's row → `claim_signal_for_execution` fails (A's row is EXECUTED) → log "already claimed or processed"
→ **B's trade is silently skipped**.
Failure 2: in channel B someone replies to B's message N, and A once had a signal N → the reply tracer (which does use
B's chat) returns root N → `get_position_by_message_id(N)` finds **A's position** → LLM context analysis → SL/TP of A's
position may be changed.
Synthetic zone ids `-(message_id * 10 + index)` (main.py:747) collide across chats the same way.
Likelihood grows with each added channel (step 18) and with time, because the DB keeps every past id.
Fix: unique `(telegram_chat_id, telegram_message_id)` (Alembic migration), and pass the chat id to every lookup.

**F20 (H) – A valid French signal within 5 min of an open trade in the same chat is swallowed as a follow-up.**
The router runs correlation **before** parsing (main.py:336-362). The time matcher's guard against new trades
(`time_matcher._looks_like_new_trade`, time_matcher.py:455-460) is a second, narrower copy of the router's rule
(`setup_aggregator.looks_like_new_trade`). It knows `buy|sell|achat|vente|long|short` and `gold|or|xau|xauusd`,
but not `vends`/`vendre`/`achète`/`acheter`. The regex parser does trade those words (patterns.py:83-97).
The matcher passes a single candidate at 0.55 (time_matcher.py:149) and the correlator then requires 0.75
(correlator.py:289). Score = 0.6 × time + 0.4 × text, ×1.1 for an open position, ×1.05 when the signal is under
2 min old. A message without any keyword (text score 0.5) clears 0.75 until the signal is about 2 min old; a message
with SL/TP words ("SL", "TP", "stop", "profit" also match the old signal's text) clears it for the whole 5-minute
window. A new signal always has SL/TP words, so it correlates.
Reproduced (`swallow.py`, real `TimeMatcher` + `RegexParser`, open SELL 3 min old in the same chat):

| Text | Regex parses | Router "new trade" | Time match |
|------|:-----------:|:------------------:|:----------:|
| `JE VENDS GOLD 4150 SL 4160 TP 4130` | SELL | yes | **0.94 → correlated, not executed** |
| `J'ACHÈTE GOLD 4150 SL 4140 TP 4170` | BUY | yes | **0.94 → correlated, not executed** |
| `SELL GOLD 4150 SL 4160 TP 4130` | SELL | yes | none → executed |

What happens next: without OpenAI the follow-up is only logged. With OpenAI the new signal's levels are offered to the LLM
as a modification of the **old** position (direction check is the only guard).
Fix: one rule. `time_matcher` calls `setup_aggregator.looks_like_new_trade` and its private copy is deleted
(story 20.1). Not changed: a new signal posted as a Telegram reply goes through reply correlation first (rare;
note for step 13).

**F21 (H) – Break-even is marked done before it is applied, and a failed move is never retried.**
main.py:1192-1199: `setup.be_done = True`, then `_apply_position_levels` per open leg, result ignored (it returns
False and logs a warning on failure). The next poll sees `be_done` and never tries again. The idle check then drops the
setup (main.py:1047-1052). A transient MT5 failure (connection blip, requote, trade context busy, market closed at
the moment TP1 fills) leaves the remaining legs at the original SL. That is a full loss instead of break-even.
Fix: set `be_done` only after every open leg's modify succeeded; on failure keep it False so the next poll retries.
Same pattern, lower impact: `_check_close_invalidation` drops the setup even when `close_position_full` failed
(main.py:1091-1097). The leg keeps its protective SL, but nothing tries the close again.

### 5.2 Medium and low

**F22 (M) – `Position.open_price` is the quoted or mid price, not the fill.** Single signals store the author's price
(main.py:1432 ← `parsed_signal.entry_price`). Setup legs store the mid price (main.py:1123, 1136 ← `get_current_price`,
which is `(bid + ask) / 2`, connection.py:991). Orders fill at ask/bid plus slippage. Break-even moves SL to this stored
price (main.py:1198), and `locks_profit` compares against it (main.py:911). So "break-even" is off by half the spread
plus slippage, and step 6's R multiple would be wrong. Fix: return the fill price from `open_market_order`
(`OrderSendResult.price`, or `positions_get(ticket)[0].price_open`) and store that.

**F23 (M) – If MT5 is not reachable at startup, it is never retried, and every MT5 call then hangs 60 s.**
connection.py:418-421: when `connect` fails, the pool still sets `_initialized = True` with an empty queue. From then on
`get_connection` waits `MT5_TIMEOUT_SECONDS` (60) and raises (connection.py:475-489). Price checks and every watcher poll
stall for 60 s; only a restart helps. Fix: leave `_initialized` False on failure (retry on next use) or reconnect
inside `get_connection`.

**F24 (M) – Messages are processed concurrently; there is no ordering per chat.** Telethon 1.40's default
(`sequential_updates=False`, client created at client.py:76) runs each update in its own task, and the poller is a
second concurrent source. Example: a follow-up ("SL 4170") that arrives while the setup message is still awaiting
correlation or the live price sees no pending setup. It goes down the standalone path and is lost.
Fix: per-chat `asyncio.Lock` in the router (fits story 19.8) or `sequential_updates=True`.

**F25 (M) – Database positions are never marked closed.** The only callers of `update_position_closed`
are in `close_processor.py` (F1, dead). Every position stays `OPEN` in the DB. A reply to an old signal finds a "open" but
closed ticket, which costs an LLM call and a failed modify. Any DB view of open positions or P&L (steps 3, 15, 16;
`get_daily_pnl`) is wrong until step 6 syncs closes from MT5. Keep `get_daily_pnl` / `get_positions_needing_sync`
for step 6, as the cross-check says, but do not trust `Position.status` before then.

**F26 (M) – A correlated follow-up changes only one leg.** `get_position_by_message_id` returns the first open position of
the signal (correlator.py:359-361), and `_handle_correlated_message` modifies that one. After a multi-leg setup has been
dropped (idle, BE done), a reply "SL 4180" moves 1 of N legs. Fix: apply to every open position of the signal
(belongs with step 13).

**F27 (M) – `cli.py stop` can kill an unrelated process.** `is_running` only checks that the PID in the file exists
(cli.py:122-126). Windows reuses PIDs, so after a crash `stop` can terminate another program (e.g. the manual MT5
terminal), and `start` can refuse with "already running". Fix: check `psutil.Process(pid).cmdline()` contains
`main.py`. Note: on Windows `os.kill(pid, SIGTERM)` is `TerminateProcess`. `shutdown()` never runs, so step 3
must persist state as it changes, not at shutdown.

**F28 (M) – Every price/candle/order call lists all broker symbols.** `_resolve_broker_symbol_name` calls
`mt5.symbols_get()` for each candidate on every call (connection.py:912). That is every 5 s per setup, twice per zone poll,
plus each order. It is a blocking call returning thousands of objects, made inside the event loop.
Fix: cache the resolved name per symbol.

**F29 (M) – Orders hard-code filling mode IOC and magic 0.** position_manager.py:383-386 and 984-987. A broker that
only allows FOK/RETURN rejects every order (retcode 10030), so each new broker profile (step 17) can hit this. With magic 0,
bot trades look like manual trades, which matters for steps 6 and 16. Fix: filling mode from `symbol_info.filling_mode`;
magic per broker instance.

**F30 (L) – Asset-specific values outside `symbol_policy`.** `formatters.PIP_SIZES` / `PRICE_PRECISION`
(formatters.py:13-30) drive `normalize_price` in the modify path. A broker name like `XAUUSD.r` falls back to 5 decimals.
`time_matcher` has its own gold regexes. Fix: rounding from `symbol_info.digits`; symbols from the policy.

**F31 (L) – Two `circuit_breaker` decorators** (`utils/circuit_breaker.py:176`, `utils/decorators.py:24`) wrap the same
class. On open/modify/close the breaker can never open, because the method bodies catch every exception (same cause as F14).
Keep one decorator.

**F32 (L) – Two dedupe stores.** `MessageHandler._processed_messages` (message_handler.py:63-71) and
`main._seen_message_keys` (F13). Keep one, in the router.

**F33 (L) – Phone number logged in plain text** (session_manager.py:88, 101, 104, 131). The coding standard says no
personal data in logs. Mask it.

**F34 (L) – `close_position_full` dead check.** `symbol_info_tick(...).bid` raises on `None` before
`if price is None` (position_manager.py:963-968) can run (the exception is caught as a generic failure). Also, a close
result of `DONE_PARTIAL` is reported as failure.

### 5.4 Checked and found fine

- Risk guard: fails closed when the MT5 snapshot is missing or the circuit is open (`_risk_guard_refusal` catches
  and `refusal(None)` refuses). Account login/mode are checked both at connect and before every order.
- Signal claim (`claim_signal_for_execution`) is an atomic `UPDATE … WHERE status = PENDING`. The same message cannot
  open twice even when push and polling both deliver it.
- Lot sizing floors to the broker step (`position_sizer.py`), so risk never exceeds the budget except at `volume_min`.
- Late SL/TP that arrive while an order is in flight are applied after the fill (main.py:1169-1174).
- MT5 connect never switches a terminal's account and refuses a demo/real mismatch (connection.py:206-251).
- Candle data drops the still-forming bar (connection.py:1034).
