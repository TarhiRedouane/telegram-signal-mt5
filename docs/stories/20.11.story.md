# Story 20.11: Next Ladder Leg Still Opens When the EXECUTED Status Write Failed - Brownfield Addition

## Status
Done

Source: story 20.9 QA Results (Quinn, 2026-10-15), follow-up item 1; roadmap step 20, item 20.11 ("Found by the 20.9 QA review on 2026-10-15 (low; fails safe)").
Depends on 20.9 (post-fill DB writes guarded). Independent of 20.10.

## Story
**As a** trader running multi-leg setups (one leg per TP, ladder across the zone),
**I want** the next leg of a setup to open even if the database failed to mark the signal EXECUTED after the first fill, and every skipped order to log its real reason,
**so that** a transient DB error (e.g. "database is locked") does not silently cut my ladder to one leg under a misleading "order not filled" log.

## What happens today (code trace, 2026-10-15)

| Step | Code | Result |
|---|---|---|
| Leg 1 fills | `_execute_signal_on_mt5` (main.py 1588-1724): claim PENDING → VALIDATED (1619), order OK, position created | Ticket open in MT5, position in `setup.positions` |
| EXECUTED write fails | 1705-1716: `update_signal_status(EXECUTED)` raises (20.9 catches it, one ERROR) | Signal row stays **VALIDATED** |
| Leg 2 due | `_fire_next_leg` → `_handle_parsed_signal(..., allow_reuse=True)` (1291-1293) → claim fails (row not PENDING) | `extra_leg = not claimed and allow_reuse and status == EXECUTED` (1621) is **False** |
| Skip | 1622-1626: INFO "MT5 execution skipped for signal N: already claimed or processed", returns `None` | |
| Setup | 1294-1296: `_disarm_or_drop(setup, "order not filled")` | Setup disarmed, log "Setup entry abandoned …: order not filled". Legs 2..N never open |

Fails safe (fewer orders, not more; leg 1 keeps break-even and invalidation), but the ladder is cut and the log points to MT5 when the cause is the DB.

Second, quieter path: `SignalRepository.update_signal_status` (repository.py 410-426) returns `False` without raising when the row is not found (`update` returns `None`).
`_execute_signal_on_mt5` ignores that return value, so the signal stays VALIDATED with **no log at all**, and leg 2 is cut the same way.

**Facts that shape the design (check in code before starting):**
- **VALIDATED is ambiguous in the DB.** It means "claimed, order in flight" as well as "filled but the EXECUTED write failed". The DB alone cannot tell them apart,
  so simply accepting VALIDATED for `allow_reuse` would also accept a signal whose first order is still in flight or never reached MT5.
- **A saved position is a durable proof.** Leg 1's `Position` row carries `signal_id`; `PositionRepository.get_positions_by_signal(signal_id)` (repository.py 521-534)
  already exists. That proof survives a crash or restart, which roadmap step 3 (persist setups, legs, TPs, break-even; reload at startup) will need: a reloaded
  setup must be able to open its next leg.
- **The process knows what it filled.** `_execute_signal_on_mt5` reaches `order_result.success` before any post-fill DB write. Recording the signal id there covers
  the case where the position row was not saved either (20.9 in-memory fallback, DB down).
- **Today setups are in memory only** (`setup_aggregator.py` 499: "pending setups lost on restart"); after a restart there is no setup to open leg 2 anyway. This
  story does not change that (roadmap step 3).
- **`allow_reuse` is only True inside a setup that already holds a position** (`bool(setup.positions)`), so the new rule cannot open an order for a fresh signal.
- **Risk guard unchanged.** The extra leg still goes through `_risk_guard_refusal` before `open_market_order`.

## Rules (the behaviour to build)

1. **Proof of fill (D1).** Checked only when the claim is lost, `allow_reuse` is True and the status is not EXECUTED, in this order:
   - **memory:** the id is in a set of signal ids filled in this run (suggested `_filled_signal_ids`), added right after `order_result.success`, before the
     position create and the EXECUTED write. Covers a position row that was not saved either (20.9 fallback). No I/O in the common same-process case;
   - **DB, only when not in the set:** `get_positions_by_signal(signal_record.id)` returns at least one position (durable: the proof a setup reloaded after a restart
     by roadmap step 3 will need). `_position_repository is None` → no DB proof, no log (same stance as 20.9). Any exception from the read → one WARNING, no DB proof.
2. **Extra-leg rule.** `extra_leg = not claimed and allow_reuse and (status == EXECUTED or proof of fill)`. Everything else in the extra-leg path is unchanged
   (no status write on refusal/rejection, no EXECUTED write after the fill).
3. **When the proof is used** (status is not EXECUTED), log one WARNING naming the source:
   `Signal N not marked EXECUTED in the DB (status=VALIDATED) but already filled (filled by this run | position in DB): opening the next leg`.
4. **Real reason on skip.** The skip log names the status: `MT5 execution skipped for signal N: already claimed or processed (status=VALIDATED)`.
5. **Silent status write.** If `update_signal_status(EXECUTED)` returns `False`, log the same ERROR as when it raises (20.9 wording, "was not marked EXECUTED (row not found)").
   Rules 1-2 then cover the next leg.
6. **Unchanged:** a lost claim with `allow_reuse=False` (single-message signals, first leg of a setup) still sends no order; a signal REJECTED before any fill is never
   reused; extra legs of a healthy DB (status EXECUTED) behave as today; the `_fire_next_leg` reason text "order not filled" stays (other causes use it; the skip
   line above it now carries the real reason).

## Acceptance Criteria

**Functional Requirements:**
1. Setup with 2 legs (e.g. `SELL GOLD 4190 4195` + SL + two TPs), EXECUTED write raising after leg 1: leg 2 opens at its level; `setup.positions` has 2 tickets;
   no "order not filled"; one WARNING (rule 3) naming the signal and status.
2. Same with `update_signal_status` returning `False` after leg 1: one ERROR "was not marked EXECUTED", then leg 2 opens.
3. Lost claim, `allow_reuse=True`, status VALIDATED, **no position in the DB and id not in the set** (order of another path still in flight): no order, skip log
   with `(status=VALIDATED)`.
4. Lost claim, `allow_reuse=False` (single-message signal), status VALIDATED, position in the DB and id in the set: no order (only setups reuse a signal).
5. Skip log always includes the status (rule 4).
6. **Restart-shaped case:** status VALIDATED, position for the signal in the DB, set **empty** (fresh process), `allow_reuse=True` → the leg opens; WARNING says
   "position in DB".
7. Position row not saved (20.9 fallback) **and** EXECUTED write failed: leg 2 still opens through the set; WARNING says "filled by this run".
8. Id not in the set and `get_positions_by_signal` raising: one WARNING, no order. Id in the set: the DB is not read at all (assert not awaited), leg opens.

## Decisions (confirmed by user 2026-10-15)
- **D1, how to know the setup's signal was filled:** the in-memory set of signal ids filled in this run, then a position for the signal in the DB when the set does
  not have it (durable, ready for roadmap step 3 reloads) (rule 1). Rejected: accept VALIDATED whenever `allow_reuse` is True (VALIDATED also means "order in flight"); memory
  set only (lost on restart, so a setup reloaded by step 3 could not open its next leg). Full persistence of setups/legs/TPs/break-even stays in roadmap step 3.
- **D2, repair the DB row on the extra leg:** no. The row stays VALIDATED; the WARNING (rule 3) makes it visible. Alternative: retry the EXECUTED write when the
  proof is used. Rejected by default: a second write against a DB that just failed adds a failure path inside the order flow for a reporting-only gain.

## Technical Notes
- **Why not change the claim in the repository:** the claim is the guard against double execution across paths; widening it to VALIDATED would weaken it for every
  caller. The fix stays in the one caller that knows it filled the order.
- **Out of scope:**
  - Positions never marked closed (F25, step 6) and other post-fill DB states.
  - Rewording the `_fire_next_leg` "order not filled" reason for the risk-guard and MT5-rejection cases (they already log their own WARNING just before).
- **Key constraints:** high-risk rule (CLAUDE.md): narrow change on the MT5 order path, every decision logged once. Risk guard stays in front of every order.

## Risk and Compatibility Check
- **Primary risk:** opening an order the claim should have blocked. Mitigation: the new path needs all of: lost claim, `allow_reuse` (setup already holds a position),
  and a proof of fill (position row for that signal, or filled by this process). AC 3 and AC 4 cover the "no" cases.
- **Secondary risk:** one extra DB read on the order path. Only on lost claims inside a setup with a non-EXECUTED status **and** an id unknown to this run (after a
  restart, or an order in flight elsewhere); a failing read is a WARNING and no order (AC 8), never an exception out of `_execute_signal_on_mt5`. The set grows by one int per filled signal per run; negligible.
- **Rollback:** `git revert` the story commit. No DB, setting or prompt change.

### Code Quality Assessment

Narrow, correct change on the MT5 order path, matching the 20.9 pattern (one log line per decision, no exception out of `_execute_signal_on_mt5`).
- The proof of fill is only evaluated on a lost claim with `allow_reuse=True` and a non-EXECUTED status (short-circuit `and`/`or`), so the common path is unchanged and
  needs no I/O. Set first, DB second, as rule 1 asks.
- `_signal_already_filled` cannot raise: a missing repository or method gives no proof, and a read error gives one WARNING and no proof. The risk guard stays in front of the order.
- `marked is False` checks only the real repository's "row not found" result, so `None` from fakes is not treated as a failure.
- The frozenset class default (dev deviation) is justified: AC 10 forbids editing `_execution_app`, which skips `__init__`. The default is immutable, so instances
  share no state, and the comment says why.

Safety checks traced in code:
- **No reuse of a rejected or expired row through the set:** every `update_signal_status` call is in `_execute_signal_on_mt5`. REJECTED is only written when
  `not extra_leg`, which needs a won claim, which needs PENDING. A row filled in this run therefore can never later read REJECTED. EXPIRED is never written.
- **Same row for every leg:** `PendingSetup.to_signal` uses `self.message_id`. A new setup from the same message starts with no positions, so `allow_reuse=False`.
- **Result:** with a failed EXECUTED write, the ladder now behaves the same as with a healthy DB.
