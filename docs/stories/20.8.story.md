## Story
**As a** trader whose bot reads signals from Telegram channels,
**I want** the polling fallback to keep running through a flood wait, a dropped connection or one bad message,
**so that** signals that push events miss are still picked up instead of being lost until the next restart.

**Existing System Integration:**
- Integrates with: `main.py` `ApplicationManager`:

    metadata (1697-1710) and passed to `_on_telegram_message` (1712); `last_seen` advanced to the newest id **after** the whole batch (1714-1716).
  - `_on_telegram_message` (263): dedupes on `"{chat_id}_{message_id}_{edit_date}"` in `_seen_message_keys`, key added **before** processing (269-273). It has no catch-all:
    an exception from correlation, the DB or `_handle_parsed_signal` propagates into the poller.
- Telethon 1.40.0: `telethon.errors.FloodWaitError` (subclass of `RPCError`) carries `.seconds`. Already imported in `src/telegram_client/client.py:17`,
  `rate_limiter.py:12`, `session_manager.py:9`.
- Technology: Python 3.12 asyncio, Telethon, pytest (`filterwarnings = error`, `asyncio_mode = auto`).
- Follows pattern: 20.5's MT5 startup retry (failure → back off 5 → 60 s, reset on success, logged) and the high-risk rule "log every decision".
- Touch points: `_poll_telegram_groups` only. No change to `_on_telegram_message`, `message_handler.py`, `client.py` or the rate limiter.

**The bug (from the code):** any exception from `get_messages` (flood wait, connection dropped during Telethon's reconnect) or from processing one message ends the
polling task for good after one ERROR line. Push events keep working, but polling exists for the case where push misses messages, so from then on missed signals are
lost until the bot restarts.

**Facts that shape the design (check in code before starting):**
- **Never poll a group with `min_id=0` unless its seed said it is empty.** `get_messages(entity, min_id=0, limit=20)` returns the 20 latest messages: replaying old
  signals in a live session could open trades on stale posts. Today a failed seed ends the task, so this cannot happen; once seeding is caught per group it can. Rule:
  a group whose seed failed stays **unseeded** (not in `last_seen`), is skipped by the poll, and its seed is retried at the start of the next iteration.
  A successful seed of an empty group stores 0 as today.
- **Dedupe makes re-fetching safe.** `_on_telegram_message` adds the key before processing, so a message that raised is not processed again when re-fetched.
  Advance `last_seen[entity_id]` after **each** message (not after the batch) so a raising message does not make the messages before it re-fetch; the ones after it are
  re-fetched next iteration and processed once.
- **Flood wait:** sleep `exc.seconds` (log WARNING with the seconds), then continue. A flood wait applies to the account, so stop the current pass over the groups and
  start the next iteration after the wait.
- **Other errors:** log one ERROR per failure with the chat id and the error (`exc_info` on the first failure of a streak only, to keep the log readable during a
  long disconnect), then back off: the iteration delay doubles from 3 s up to 60 s while failures continue and goes back to 3 s after a pass with no failure.
  Log one INFO when polling recovers after a streak.
- **Cancellation:** `asyncio.CancelledError` must still stop the task (it is a `BaseException`, so `except Exception` does not catch it); keep the existing
  "Telegram polling fallback stopped" INFO.
- **Not in scope:** rate limiting the poll calls (`rate_limiter.human_delay()`, decision F18 in story 19.5); moving the poller out of `main.py` (19.5); the metadata
  builder duplication (F7, 19.5); a catch-all inside `_on_telegram_message`.

## Acceptance Criteria

**Functional Requirements:**
1. An exception from `get_messages` during polling (not seeding) logs one ERROR naming the chat and the error; the task keeps running and polls again.
2. `FloodWaitError` from `get_messages` (seed or poll) logs one WARNING with its seconds, sleeps that long, and polling continues afterwards.
3. Consecutive failed passes back off 3 → 6 → 12 → … → 60 s (cap); the first pass with no failure resets the delay to 3 s and logs one INFO "recovered".
4. A failed seed leaves that group unseeded: it is never polled with `min_id=0`, its seed is retried on the next iteration, other groups are seeded and polled normally.
   A seed that succeeds on an empty group stores 0 as today.
5. An exception from `_on_telegram_message` for one message is logged (ERROR with chat and message id) and does not stop the task; earlier messages of the batch
   are not re-fetched; later ones are processed on the next iteration; the failing one is not processed twice (dedupe).
6. Cancelling the task still raises `CancelledError` out of `_poll_telegram_groups` and logs "Telegram polling fallback stopped".

**Integration Requirements:**
7. Unchanged when nothing fails: same seeding log lines, same 3 s interval, same `get_messages` arguments, same metadata passed to `_on_telegram_message`, messages
   processed in id order, `last_seen` ends at the newest id.
8. `_on_telegram_message`, `message_handler.py`, `client.py`, the rate limiter and the push path are not edited. Existing tests pass without edits.

## Technical Notes
- **Why skip an unseeded group instead of polling it with `min_id=0`:** the first poll would return the 20 latest posts, some of which can be complete signals from
  hours ago. `_on_telegram_message` checks the DB (`find_by_message_id`, 325) only for edited messages, and its in-memory dedupe is empty after a restart, so nothing else blocks a replay. Skipping until the seed works
  loses nothing: push events still deliver new messages, and the seed's latest id becomes the starting point.
- **Why per-message `last_seen`:** with the batch-level update a raising message would make the whole batch re-fetch; dedupe would skip the processed ones, so this is
  about less work and clearer logs, not correctness.
- **Why not reuse `RateLimiter.handle_flood_wait`:** it needs a `RateLimiter` instance the app does not hold and adds a 1.5× buffer; the poller waiting exactly
  `seconds` before its next 3 s cycle is enough. Unifying belongs to F18 / 19.5.
- **Key constraints:** high-risk rule (CLAUDE.md): Telegram code, narrow and observable change; every failure logged with the chat id. Complete single-message
  signals and multi-message setups must keep working (no change to `_on_telegram_message`).

## Risk and Compatibility Check
- **Primary risk:** replaying old messages after a failed seed (stale signals traded). Mitigation: unseeded groups are never polled (AC 4 test asserts no `min_id=0` call).
- **Secondary risk:** a tight error loop hammering Telegram during an outage (ban risk). Mitigation: back-off to 60 s and honouring flood waits (AC 2-3).
- **Rollback:** `git revert` the story commit. No DB or setting change.
