## Story
**As a** trader running the signal bot,
**I want** each stored position to carry the price MT5 actually filled at,
**so that** break-even, profit-lock checks and later R-multiple maths use the real entry, not the quote the order was aimed at.

## Story Context

**Existing System Integration:**
- Integrates with: `src/mt5_executor/position_manager.py` `MT5Result` (29-45) and `open_market_order` (297-454, success return at 436);
  `main.py` `_execute_signal_on_mt5` position create (~1494-1498, `open_price=float(parsed_signal.entry_price)`).
- Readers of `Position.open_price` that get fixed by this change without edits: `main.py:529` (follow-up SL/TP sanity check),
  `main.py:918` (`locks_profit`), `main.py:1242` (setup break-even), `src/risk_manager/break_even.py:208-245`,
  `position_modifier.py`, `context_processor.py:344`, `context_analyzer.py:282`.
- Technology: Python 3.12, `MetaTrader5` module (mocked in tests), pytest (`asyncio_mode=auto`, `-W error`).
- Follows pattern: `MT5Result` already carries `close_price` for closes; open gets the same kind of field. High-risk rule (CLAUDE.md):
  narrow change, log the decision.
- Touch points: `MT5Result` (one new field), `open_market_order` (read the fill), `main.py` (one line + one log). No schema change.

**The bug (from the code):**
1. Single signals store the author's price: `open_price=float(parsed_signal.entry_price)` (main.py ~1498).
2. Setup legs store the mid price: `_fire_next_leg` sets `signal.entry_price = price` (main.py ~1157/1170) where `price` comes from
   `get_current_price` = `(bid + ask) / 2` (connection.py:943+). The same `entry_price` then reaches the same `open_price` line.
3. The order itself goes out at `tick.ask` (BUY) or `tick.bid` (SELL) with IOC filling (position_manager 374-386) and can fill with slippage.
4. Break-even moves SL to `position.open_price` (via `_apply_position_levels(..., Decimal(str(position.open_price)))`, main.py ~1242, and `break_even.py`).
   So "break-even" is off by about half the spread plus slippage. `locks_profit` compares against the same wrong value.
5. Roadmap step 6 (R multiple) would inherit the error.

**Facts that shape the design (check in code before starting):**
- `mt5.order_send` returns an `OrderSendResult`; for a market deal `result.price` is the deal price. Some brokers (market execution)
  can return `0.0` there, so a fallback is needed: `mt5.positions_get(ticket=<ticket>)[0].price_open`.
- `result.order` is used as the ticket today and is the position ticket on hedging accounts (already how `open_market_order` works; the
  filling mode and magic number are F29, out of scope).
- `Signal.entry_price` is the author's / aimed price and stays that way: it is signal data, not trade data.

## Acceptance Criteria

**Functional Requirements:**
1. `MT5Result` has a new optional field `fill_price: float | None = None` (default keeps every other `MT5Result` construction valid).
2. `open_market_order` sets `fill_price` on success: `getattr(result, "price", None)` when it is a real number (`int`/`float`) and > 0;
   otherwise `positions_get(ticket=ticket)` first row's `price_open` under the same number check; otherwise `None`. The number check
   matters: existing tests use `MagicMock`/`SimpleNamespace` results with no `price`, and a `MagicMock` converts to `1.0`. A failure in the
   fallback lookup never turns a filled order into a failed one.
3. `main.py` stores `open_price = order_result.fill_price` when present. When `None`, it falls back to the old value
   (`parsed_signal.entry_price`) and logs one WARNING that the quote was used.
4. When the fill price is known, log one INFO line with ticket, requested (aimed) price and fill price, so slippage is visible.
   Secrets/ids: no new fields beyond ticket and prices.
5. Setup legs (zone ladder) and single signals both go through the same line, so both store the fill. No separate change in `_fire_next_leg`.
6. Partial fills (`TRADE_RETCODE_DONE_PARTIAL`): the stored price is the price returned for that deal; no volume change in this story.

**Integration Requirements:**
7. No change to order request, volume, SL/TP sent, filling mode, retry/circuit-breaker wiring, parsing, scoring or the DB schema.
8. `Signal.entry_price` is unchanged. Only `Position.open_price` differs.
9. Positions already stored keep their old `open_price`; no backfill (see Technical Notes).
10. Break-even and close logic read `position.open_price` as before; behaviour changes only through the corrected value.

**Quality Requirements:**

## Technical Notes
- **Why not read the fill later (poll `positions_get`):** the order result already holds the price; a second call adds a failure mode. The
  `positions_get` lookup is only the fallback for brokers that return `0.0`.
- **Why `Signal.entry_price` stays:** it is what the author said; the correlator and context analyzer use it. Only the trade record changes.
- **No backfill (confirmed by user 2026-10-12):** the bot runs on demo accounts with test signals, so existing rows are not corrected.
  A reconcile from MT5 `price_open` can join the restart-state work (roadmap step 3) if ever needed.
- **Break-even semantics unchanged:** SL goes to the entry (fill) price. Whether to add spread/commission to BE is a strategy choice, not this story.
- **Out of scope:** filling mode and magic number (F29), partial-fill volume handling, `positions` never marked closed (F25),
  per-leg update (F26), MT5 startup (20.5), PID check (20.6).
- **Key constraints:** high-risk rule (CLAUDE.md): narrow, observable change. Never log API keys.

## Risk and Compatibility Check
- **Primary risk:** a wrong price stored (for example `result.price` is the requested price on some brokers, or a zero), which would move
  break-even to a bad level. Mitigation: positive-number check, `positions_get` fallback, fall back to the old quote with a WARNING, tests for all three paths.
- **Secondary risk:** `positions_get(ticket=...)` raises or is slow inside the order path. Mitigation: only called when `price` is not positive; wrapped, returns `None`.
- **Rollback:** `git revert` the story commit. No DB change to undo; stored rows stay valid either way.

**Compatibility Verification:**

- [ ] Performance: no extra MT5 call on the normal path

### Code Quality Assessment
Small change in the right place. `_fill_price` sits next to the only `order_send` for entries, runs inside the same connection context, and
cannot fail a filled order (fallback wrapped, `None` on any doubt). `main.py` has one writer of `open_price` (re-grepped: `main.py:1508`
only), so single signals and setup legs both get the fill without touching `_fire_next_leg`. `MT5Result.fill_price` is the last field
with a default, so every other `MT5Result(...)` construction stays valid. `getattr(order_result, "fill_price", None)` keeps the
`SimpleNamespace` doubles in `test_risk_guard.py` working. `ParsedSignal.entry_price` is a `Decimal` defaulting to `0.0`, never `None`,
so the `float(...)` in the INFO/WARNING lines cannot raise.

Side benefit: a signal with no price (`entry_price == 0`) used to store `open_price = 0.0`, and break-even would then send SL to 0. With a
known fill it now stores the real price. The fallback path still stores `0.0` in that case (pre-existing, logged as WARNING).

API semantics: Context7 was unavailable (invalid API key). From the MQL5 `MqlTradeResult` reference, `price` is the deal price confirmed by
the broker and can be `0` on Market execution, which matches the story's fallback. Not proven against this broker: see the manual check below.
