## Story
**As a** trader running one bot process per broker,
**I want** `cli.py stop` and `cli.py start` to act only on a process that really is this bot,
**so that** a stale PID file (after a crash or reboot) can never make `stop` kill another program, such as the manual live MT5 terminal,
and never makes `start` refuse with "already running".

## Story Context

**Existing System Integration:**
- Integrates with: `cli.py` `SignalEAManager`: `is_running` (122-126), `get_pid` (128-133), `stop` (78-112), `start` (41-76), `status` (115-120).
  The PID file is written only by `start` (line 73: `process.pid` of the `Popen` of `sys.executable <PROJECT_ROOT>/main.py`).
  Nothing else in the repo reads or writes `signal_ea.pid` (grep of `*.py`, `*.md`, `*.bat`, `*.ps1` outside `.venv`).
- Technology: Python 3.12, `psutil==6.1.0` (already in `requirements.txt` and already imported in `cli.py`), pytest.
- Follows pattern: existing `psutil.pid_exists` check in `is_running` (comment there: `os.kill(pid, 0)` is unsafe on Windows).
- Touch points: `SignalEAManager.is_running` only. `stop`, `start` and `status` all call it, so one fix covers all three. No new setting, no new file.

**The bug (from the code):**
1. F27. `is_running` returns `pid is not None and psutil.pid_exists(pid)`. It never checks what the process is. Windows reuses PIDs.
   After a crash or a hard kill, `shutdown()` never ran and the PID file stays. If that PID now belongs to another program:
   - `stop` sees "running", sends `os.kill(pid, SIGTERM)` (on Windows this is `TerminateProcess`) and, if still alive after 10 s, kills it again.
     The victim can be the manual live MT5 terminal (see project memory: live MT5 is manual-only).
   - `start` prints "already running" and does not start the bot.
2. `stop` removes the PID file only after the kill attempt. When the check is fixed, the "not running" branch (80-84) already deletes the
   stale file, so no new cleanup code is needed.

**Facts that shape the design (check in code before starting):**
- All broker instances run the same script, `main.py`, so the command line cannot tell broker A from B. It does not need to: each instance
  has its own PID file (`data/<instance>/signal_ea.pid`). The check only answers "is this PID a bot process at all".
- `start` launches `[sys.executable, str(PROJECT_ROOT / "main.py"), ...]` with an absolute path. Match on that exact path (normalised, case-insensitive on
  Windows), not on the bare name `main.py`: another project's `main.py` must not count.
- `psutil.Process(pid).cmdline()` can raise `NoSuchProcess` (gone between the two calls), `ZombieProcess`, or `AccessDenied` (process of another
  user or protected). All three mean "not our bot" for this purpose.
- Windows venv: `venv\Scripts\python.exe` may be a launcher that starts the real interpreter as a child. Its own command line still holds the
  script path, so the recorded PID matches. Dev confirms on the real terminal (manual check below).
- Do not log the other process's command line (it may hold secrets). Log its name only.

## Acceptance Criteria

**Functional Requirements:**
1. `is_running()` returns `True` only when the PID file holds a PID that exists AND whose command line contains an argument naming
   `PROJECT_ROOT/main.py`. A missing PID file, an invalid PID, a missing process, an unreadable command line (`AccessDenied`,
   `ZombieProcess`, `NoSuchProcess`) or a different command line all give `False`.
2. `stop` on a stale PID (PID reused by another program) sends no signal at all, prints "<name> is not running", and removes the PID file.
3. `start` on a stale PID (PID reused) starts the bot normally and overwrites the PID file. It does not print "already running".
4. When the PID exists but belongs to another program, log one WARNING with the PID and the process name (not the command line):
   "PID <n> in <pid_file> is not the bot (<process name>); ignoring stale PID file". No log when the PID simply does not exist.

**Integration Requirements:**
5. A genuine bot process is still detected: `status` shows running, `stop` terminates it, `start` refuses a second copy. The force-kill loop in
   `stop` (10 x 1 s wait, then kill) behaves as today for the real bot.
6. No change to `start`'s `Popen` call, to the menu/target logic, to `get_pid`, or to any file outside `cli.py` and its test.

**Quality Requirements:**
7. New tests fail on the base commit (record in Dev Agent Record). Cases in Task 1.
8. Full `pytest` stays green (baseline: 735 passed, 6 skipped per 20.5, plus the QA test added there; record the exact count).

## Technical Notes
- **Why path match, not name match:** `main.py` is a common script name. The full path ties the check to this checkout, which is what `start` launches.
- **Why not store the process start time in the PID file:** it would also catch a reused PID that happens to run this same `main.py`, but
  that needs a new file format and a migration for existing PID files. The command-line check closes the real hole (unrelated programs). Add it only if a second bot
  checkout on the same machine ever shares a data folder.
- **Race left open:** the process can change between the check and `os.kill`. The window is microseconds, far smaller than the hours-long stale-file
  window being closed. Not worth a lock.
- **`stop` kills without `shutdown()`:** on Windows `os.kill(pid, SIGTERM)` is `TerminateProcess`, so the bot never runs its shutdown code. State must be
  persisted as it changes (roadmap step 3). Not fixed here.
- **Out of scope:** graceful stop (CTRL_BREAK or a stop file), `status` showing a "stale PID" line, `--daemon` flag behaviour, per-chat ordering (F24).
- **Key constraints:** high-risk rule (CLAUDE.md): narrow change. This code can terminate processes, so the safe default on any doubt
  (cannot read the command line) is "not our bot, do not kill".

## Risk and Compatibility Check
- **Primary risk:** a false negative: a real bot is judged "not running", so `stop` leaves it alive and `start` launches a second copy for the same
  broker (two bots on one Telegram session and one MT5 terminal). Causes: command line in an unexpected form (relative path, venv launcher, symlinked checkout).
  Mitigation: match on the exact absolute path `start` itself builds; test with a real spawned process; manual check on the real terminal.
- **Secondary risk:** `AccessDenied` on a real bot started elevated while `cli.py` runs unelevated. It would read as "not running". Both start from the
  same user in the normal flow; noted, and the WARNING makes it visible.
- **Rollback:** `git revert` the story commit. No DB or setting change to undo.

### Code Quality Assessment
Fixed in the one function that `stop`, `start` and `status` all route through, so the stale-PID path reuses `stop`'s existing
"not running" branch with no new cleanup code. Safe default on doubt (`psutil.Error` → not the bot) is right for code that kills
processes. The command line is never logged; only the process name. The dev checked the venv launcher before coding, which
answered the story's main risk with evidence instead of a guess. Tests use real processes and keep the PID file in `tmp_path`.

One defect found and fixed (below): `abspath()` resolved another process's relative arguments against the CLI's own cwd.

### Refactoring Performed
- **File**: `cli.py` (`is_running`)
  - **Change**: compare `os.path.normcase(arg)` to the absolute `PROJECT_ROOT/main.py`; dropped `os.path.abspath(arg)`.
  - **Why**: `abspath("main.py")` resolves against the CLI's working directory, not the target process's. `cli.py` is normally run
    from the project root, so any reused PID running some other project's `python main.py` (relative) matched as the bot, and
    `stop` would kill it: the F27 hole, narrower but still open.
  - **How**: `start` always launches with the absolute path `str(PROJECT_ROOT / "main.py")`, and `PROJECT_ROOT` is the same resolved
    path in every CLI run, so an exact (case-normalised) match is both sufficient and strict. Comment explains why `abspath` is absent.
- **File**: `tests/unit/test_cli.py`
  - **Change**: added `test_relative_main_py_of_other_project_is_not_the_bot`; `spawn` fixture takes `cwd=`.
  - **Why**: proves the hole: fails on the dev's version (`assert True is False`), passes after the change.
