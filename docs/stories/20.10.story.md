## Story
**As a** trader whose channel announces a direction first ("sell gold now") and gives the entry price in the next message ("4146"),
**I want** the bot to hold that direction as a pending setup, wait for the entry price, and open the trade only when the market is close to that price or better,
**so that** the first message is no longer lost, and the bot never sells or buys at a random market price before the author has said where.

**Facts that shape the design (check in code before starting):**
- **Today "now" means fire at market.** A setup whose opener says "now" gets `fire_now=True`, and `_fire_next_leg` opens leg 1 at the next poll whatever the price.
  So simply teaching the regex to parse "sell gold now" would sell at market at once. That is exactly what the user does not want.
- **Today `sell gold now` after a fill also sells at market (D4).** While a filled setup is still tracked (at least 5 min after its last update, longer with several legs
  before break-even), `sell gold now` has no price, so it is not a new trade (`looks_like_new_trade`). It goes to `_handle_setup_followup`, which sees "sell" + "now",
  calls `reopen()` and sets `fire_now`. The next poll sells at market.
- **Today `buy gold now` during a pending SELL setup fires the SELL (D5).** Same route: no price → follow-up of the SELL setup → `extract_followup` only sees "now" →
  `fire_now=True` → the **SELL** leg fires at the next poll. With this story and no fix, the next `4146` would set the entry of the SELL setup: the bot would sell
  where the author meant to buy.
- **No price, no live price check.** `_validate_live_price` compares `entry_price` with the market. A price-less signal would carry `entry_price = 0` (LLM parser and
  `ParsedSignal` default) and be rejected for deviation. The new opener must not go through `_validate_live_price`, nor through `SetupAggregator.start` with a
  `ParsedSignal` (that gives `low = high = 0`, not "unknown"); build the `PendingSetup` directly. It still needs an enabled symbol.
- **A complete single-message signal always has a price.** The new branch only matches messages with **no 4-digit number at all**, so it can never catch
  `sell gold 4149\nSL 4165\nTP 4115` (regression guard, memory "Signal formats" rule 1).
- **A bare number reaches the LLM today.** Inside a setup, `extract_followup("4146")` is empty (`FOLLOWUP_ENTRY` needs a word such as "entrer"/"sell"), so
  `_llm_setup_followup` runs, and an LLM CLOSE there **cancels the setup**. The bare-price rule must run before the LLM.
- **`action_side` matches negations and commentary (checked 2026-10-15).** `action_side("je ne vends pas gold")` and `action_side("gold sell-off")` both return SELL
  (`vend(?!redi)\w*` matches "vends"; `\bsell\b` matches before the hyphen). The opener needs its own guard.
- **"Better" needs a ceiling.** For a SELL, a higher market is a better price, but a market far above the entry means the move went against the idea. With an SL known,
  `fire_levels` already refuses a price at or beyond it. With no SL, the ceiling is the default SL distance from the entry (gold 10.0 points), read from `symbol_policy`.

## Rules (the behaviour to build)

Names below are suggestions; keep the smallest change that gives this behaviour.

1. **Price-less opener.** A message with exactly one side word (`action_side`), an enabled symbol alias as a whole word, **no 4-digit number** (`_PRICE`), **no negation**
   (`ne`/`pas`/`not`/`don't`/`no` within 3 words before the side word) and **no hyphen right after the side word** (`sell-off`). When the chat has **no pending setup and no
   zone watch**, it starts a setup that waits for its entry: same side and symbol, `low`/`high` unknown (`None`), `fire_now=False` even if the text says "now"/"maintenant",
   and a flag such as `await_entry=True`. No order, no LLM call, no live price check. Examples: `sell gold now`, `SELL GOLD NOW`, `je vends gold maintenant`,
   `buy xauusd now`, `sell gold`.
2. **Entry arrives.** While the setup has `await_entry` set (entry unknown, or entry known but no fill yet), a follow-up that is only a price (`4146`, `4146.5`, `4146,5`)
   or a price range (`4146-4150`, `4146 - 4150`, `4146–4150`) sets or replaces the entry, before any LLM call. The existing `FOLLOWUP_ENTRY` phrasing (`entrer à 4146`,
   `sell 4146`), a same-side new trade (`sell gold 4146`, through `start`/`rearm`) and an edit of the opener (`sell gold now` edited to `sell gold now 4146`, through
   `_handle_setup_edit`) also set it, and `await_entry` stays set. Log one INFO line: `Setup entry received chat=… entry=4146(-4150), waiting for price close or better`.
3. **SL/TP before the entry.** `sl 4165`, `TP 4115`, "je vise 4110" received while the entry is unknown are stored (no wrong-side check yet, there is no entry to check against).
   When leg 1 fires, `fire_levels` checks them against the fill price as it does today (wrong-side SL → setup dropped "invalidated"; wrong-side TP → leg sent without TP).
4. **When leg 1 fires (only for `await_entry` setups).** Let `entry` = the first ladder level (`legs()[0]`; the low edge of a SELL range, the high edge of a BUY range),
   `tol` = `get_entry_tolerance`, `cap` = `get_default_sl_distance`.
   - SELL fires when `entry - tol <= price <= entry + cap`. BUY fires when `entry - cap <= price <= entry + tol`.
   - "Close" = within `tol` on the worse side. "Better" = up to `cap` on the better side. Outside that band: keep waiting, no log per poll.
   - This rule replaces both `fire_now` and the complete-setup "live price check only" path for these setups, so SL+TP being known does not fire it early.
   - Log one INFO line when it fires: `Setup firing chat=… SELL price 4147.2 vs entry 4146 (better by 1.2)` (or "close").
5. **Unchanged for these setups:** default SL when none received, leg count and ladder (legs 2..N keep `leg_reached`), blind first leg half risk when no TP,
   break-even at TP1, cancel phrases ("annuler le setup"), a priced opposite-side signal replacing the setup.
6. **No entry ever arrives.** The setup expires with the existing idle timeout (300 s from the last update) as "expired before entry". No trade. (Decision D1.)
7. **Same-side opener after a fill (D4).** The chat's setup has positions and is not armed, and a price-less opener (rule 1 test) of the **same side and symbol** arrives:
   `reopen()` for one extra order, entry unknown, `await_entry=True`, `fire_now=False`. Rules 2-4 then apply to that re-entry. Open positions keep their SL/TP and
   break-even tracking. Only the full opener form (side + symbol, no price) changes; `vends maintenant` / `sell now again` (no symbol) and `sell now 4144` (with a price)
   keep today's re-entry behaviour.
8. **Opposite-side opener while a setup exists (D5).** A price-less opener (rule 1 test) of the **opposite side** never folds into the current setup. It replaces it with a new
   `await_entry` setup, the same way a priced opposite-side signal does today (`SetupAggregator.start`: log "Replacing setup … (different side/symbol)", the old watcher
   stops). If the old setup had positions, log one WARNING with their tickets: they keep their MT5 SL/TP but lose break-even tracking (same as a priced opposite signal today).

## Technical Notes
- **Why a router branch and not a regex pattern returning a `ParsedSignal`:** a `ParsedSignal` with no price would flow into `_validate_live_price` and the instant path,
  which both need an entry. A setup that waits is what the user described, and the setup machinery already polls price, expires and fires legs.
- **Why the branch sits before the pending-setup follow-up:** D4 and D5 need to see the opener before `_handle_setup_followup` turns its "now" into `fire_now`. Placing it
  before the correlation engine also stops a reply-chain or time-window match to an open GOLD position from swallowing the opener.
- **Why the band also overrides the complete-setup path:** a complete setup normally fires on the live check alone (up to 100 points away). For a setup whose author gave the
  entry after "now", that would sell far from the stated entry, which is what the user wants to avoid.
- **Out of scope:**
  - Openers with SL/TP but no entry (`sell gold now SL 4165 TP 4115`): `FOLLOWUP_ENTRY` would read 4165 as the entry, which needs its own parsing rules. They stay as today
    (regex miss, LLM, rejected by the live price check). Candidate follow-up story.
  - `sell gold now` in a same-side setup that **already has a price** and no fill (`SELL GOLD 4150`, then `sell gold now`): keeps today's `fire_now` market fill. Candidate
    follow-up if the user wants the band there too.
  - "now" with a price (`you can sell now 4144`), `vends maintenant` re-entry after a fill, and the zone "buy now" early leg: unchanged (AC 14).
  - LLM CLOSE for a bare number (cached for `4146` without context): handled while `await_entry` is set (rule 2 runs first). In other setups (priced, or after the
    `await_entry` fill) a bare number still reaches the LLM, and a CLOSE answer still cancels the setup, as today. A guard requiring a close/cancel word stays a follow-up.
  - A complete same-side signal arriving while a setup is pending executes on the instant path and does not drop the setup. That is existing behaviour for every setup type;
    log it for step 19/20 review, do not change it here.
- **Key constraints:** high-risk rule (CLAUDE.md): narrow change in the Telegram → MT5 path, every decision logged once. Complete single-message signals and multi-message setups
  must keep working (AC 14). Regex before LLM: the new opener and bare-price rule are regex only.

## Risk and Compatibility Check
- **Primary risk:** the new opener catches a message that is not a trade order (commentary such as "gold sell-off", "je ne vends pas gold"). Mitigation: rule 1 negation and
  hyphen guards, one side word only, enabled symbol as a whole word, no price; the setup still needs an entry price before any order and expires after 5 min. Negative cases
  in Task 1 (AC 10).
- **Secondary risk:** D5 replacing a filled setup drops break-even tracking of its open positions. Mitigation: same behaviour as a priced opposite signal today; one WARNING
  with the tickets; MT5 SL/TP stay on the positions.
- **Third risk:** `None` entry reaching code that does arithmetic on `low`/`high`. Mitigation: Task 2 guards every reader; tests run SL/TP-before-entry sequences (AC 5).
- **Rollback:** `git revert` the story commit. No DB, setting or prompt change.

### Code Quality Assessment

Narrow change that matches rules 1-8. The new router branch sits before the pending-setup follow-up and the correlation engine, as the story requires, and only
runs for a price-less opener; every other message takes today's path (AC 14 tests pass on base and after). The unknown entry is modelled as `low/high = None` plus
`await_entry`, and every reader is guarded (`legs`, `in_entry_zone`, `apply`, the LLM context, `_fire_next_leg` early return), so a `None` cannot reach arithmetic.
Leg 1 of an `await_entry` setup goes through `entry_gap` then the existing `fire_levels` / `to_signal` / `_handle_parsed_signal` path, so the risk guard and sizing are
unchanged. Clearing `await_entry` and `fire_now` together at the fill is the right call. Asset values come only from `symbol_policy` (AC 15). Each decision logs one
line (started / entry received / firing / replaced + WARNING with tickets), which the demo log confirms.
