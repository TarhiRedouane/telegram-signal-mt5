# Story 1.4: Health Monitoring and Logging System

## Status
Done

## Story
**As a** system operator,  
**I want** comprehensive logging and health checks,  
**so that** I can verify the system is running correctly.

## Acceptance Criteria
1. Health check runs every 60 seconds confirming Telegram connection
2. Structured logging captures all messages, errors, and system events
3. Log rotation prevents disk space issues (max 100MB per file, 5 file rotation)
4. Console dashboard shows: connection status, messages/minute, last signal time, uptime
5. Error alerts logged with ERROR level for connection failures or exceptions
6. Graceful shutdown handler saves state and closes connections properly

### Structured Logging Requirements
**Source:** [Source: architecture/error-handling-strategy.md#logging-standards]
**JSON Log Format Required:**
```json
{
  "timestamp": "ISO8601",
  "level": "ERROR", 
  "component": "str",
  "message": "str",
  "context": {
    "correlation_id": "UUID per signal lifecycle",
    "service_context": "Component name, method, line number",
    "user_context": "Telegram sender (hashed), signal group"
  }
}
```

**Log Levels:** DEBUG (dev only), INFO (operations), WARNING (degraded), ERROR (failures), CRITICAL (system down)

### Coding Standards Requirements
**Source:** [Source: architecture/coding-standards.md]
**Critical Rules for This Story:**
- **Never use print() for output - use logger:** All dashboard output must integrate with logging system
- **All async functions must handle cancellation:** Health checks and metrics collection must cleanup on cancel
- **Never log sensitive data:** Hash telegram usernames, sanitize any user data in logs
- **All external API calls must use circuit breaker decorator:** Health checks to external systems must be protected
- **Database operations must use repository pattern:** Any persistence for metrics must go through repository

### Error Handling Strategy
**Source:** [Source: architecture/error-handling-strategy.md]
**Error Handling Patterns:**
- **Retry Policy:** Exponential backoff: 1s, 2s, 4s, 8s, then circuit break
- **Circuit Breaker:** Open after 5 consecutive failures, half-open after 30s
- **Custom Exceptions:** Create monitoring-specific exceptions for health check failures
- **Error Translation:** Map external connection errors to internal error codes
