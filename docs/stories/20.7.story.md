## Story
**As a** trader who risks a fixed 3 % per signal,
**I want** a complete single-message signal (`sell gold 4150 / SL 4160 / TP 4130`) to be sized and risk-checked on the price the order will really fill at,
**so that** a signal posted a few points away from the market never loses more than the risk budget at its SL, and the open-risk cap counts the real loss,
**and** the stop is never tighter than 20 pips from the market unless the author's own stop is tighter (added v0.4, user decision 2026-10-15).

## Story Context

**Existing System Integration:**
- Integrates with: `main.py` `ApplicationManager`:
  - router branch for complete signals: `_on_telegram_message` 409-421 (`_validate_live_price` then `_handle_parsed_signal`);
  - `_validate_live_price` 1317-1362 (reads the live price, compares it with the post's entry, returns only `bool`);
  - `_handle_parsed_signal` 1364 → `_execute_signal_on_mt5` 1418 → `_order_volume` 1288 (called at 1463 when no volume is passed) and
    `_risk_guard_refusal` 1271 (called at 1464).
- Technology: Python 3.12 asyncio, `Decimal`, pytest. Sizing: `src/risk_manager/position_sizer.py::leg_volume`. Guard: `src/risk_manager/risk_guard.py::order_risk`.
- Follows pattern: leg 0 of a complete setup (`_fire_next_leg`, main.py:1153-1157): `signal = setup.to_signal(entry=setup.low, ...)`,
  `_validate_live_price(signal)`, then `signal.entry_price = price`, so sizing and risk guard see the live price.
- Touch points: the router's complete-signal branch and `_validate_live_price`. `position_sizer.py`, `risk_guard.py`, `position_manager.py` stay unchanged.

**The bug (from the code):**
1. F35. For a single-message signal, `signal.entry_price` is the number written in the post. `_order_volume` computes
   `sl_distance = abs(entry_price - stop_loss)` (main.py:1307) and `_risk_guard_refusal` computes `entry_price - stop_loss` (main.py:1281), both from that number.
   The order itself fills at `tick.bid` / `tick.ask` (position_manager.py:375). The gap between the two is what `_validate_live_price` allows:
   up to `GOLD_MAX_PRICE_DEVIATION` = **100** points (`config/settings.py:65`, `.env.example:54`, and the user's `.env`).
2. Example: `SELL GOLD 4150 SL 4160 TP 4130`, market 4135. Sized for a 10-point stop, real stop 25 points. Balance 10,000, `RISK_PERCENT` 3,
   tick size 0.01, tick value 1: lot 0.30 (budget 300 / 1,000 per lot). Real loss at SL: 0.30 × 25 pts × 100 = **750 = 7.5 %**. The guard added only 300 to open risk,
   so `MAX_OPEN_RISK_PERCENT` (6 %) does not catch it.
3. Setups are already right: leg 0 replaces the entry with the live price before sizing (main.py:1157), and later legs use the polled price as entry.
   Only the router's complete-signal branch is affected. Nothing else calls `_handle_parsed_signal` without a live price.

**Facts that shape the design (check in code before starting):**
- **Which price:** `get_current_price` = mid of bid/ask (connection.py:975). Setups use the same price. The order fills at ask (BUY) or bid (SELL), so the real distance differs
  by half the spread plus slippage (about 0.1-0.3 points on gold). Accepted residual.
- **Where the live price is replaced: only in the complete-signal `else` branch** (main.py:420-421), not inside `_validate_live_price`. That function runs for every BUY/SELL, including
  the ones routed to `_start_setup` (missing SL/TP, multi-TP, SL range, candle-close SL), and `_start_setup` builds the setup's entry zone from `parsed_signal.entry_price`
  (`SetupAggregator.start`). Overwriting the entry inside the validator would replace the author's zone with the market price. Do not do that.
- **`_validate_live_price` stays as it is** (returns `bool`, not edited). About 11 existing tests patch it with `AsyncMock(return_value=True)` (`test_setup_aggregator.py`,
  `test_time_matcher_new_trade.py`), and `_fire_next_leg` uses it as `not await ...`. Returning a price from it would turn those `True` values into entry prices.
- **So the branch reads the live price itself:** one extra `get_current_price` call (the validator's read is not returned), via a small helper next to `_validate_live_price`. The
  two reads are milliseconds apart. If the helper cannot get a price (MT5 manager missing or `None` price) the signal is rejected like a failed live-price check (fail closed).
  Tests that reach this branch with a `MagicMock` manager need `get_current_price` as an `AsyncMock`; a fixture-only edit like that is allowed and is listed in the File List.
- **The signal row then stores the live price** (as setup signals already do); the author's entry stays in `raw_text` and goes into the log line (AC 5).
- **No DB constraint** ties `entry_price` to `stop_loss` direction (`models.py:128-158`: only a confidence-score check), so a live price on either side of the SL does not break `save_signal`.
- **Sizer safety net:** `leg_volume` returns `volume_min` when `sl_distance / tick_size * tick_value <= 0` (position_sizer.py:21-23). A live price exactly at the SL would size at the minimum lot,
  so the "market at or beyond SL" case needs its own refusal (AC 4) instead of relying on the sizer.
- **No persistence on refusal:** the signal is saved inside `_handle_parsed_signal`, after this branch. A refusal here is a log line only, exactly like the existing
  "Signal rejected - live price check failed" (main.py:422-426). It is not stored as REJECTED.
- **Risk guard, why the test must spy:** after the fix volume and guard both use the live distance, so `new_risk` is 300 (3 %) with or without the fix for the sized volume. The defect shows in the
  *distance* the guard and sizer are given (10 vs 25 points) and in the lot, not in the guard's outcome. Test the arguments, not the verdict.

**Minimum stop (added v0.4; user decision 2026-10-15, after QA showed 0.5-2 point stops getting 1.5-6 lots):**
- **Rule:** after sizing moved to the live price, a market that has moved toward the SL leaves a tiny stop and a huge lot. The user's rule: the stop is at least **20 pips** from the
  market; if it is closer, move the SL further from the market to exactly that distance and size the lot on it. **Unless the author chose a tighter stop:** when the post's own
  `|entry - SL|` is under 20 pips (e.g. 15 pips), that distance is the minimum instead. Minimum = `min(20 pips, post's own |entry - SL|)`.
- **Pips:** for gold 1 pip = **0.10**, so 20 pips = **2.0 price units** (`settings.py:67` comment "10.0 = 100 pips at 0.10/pip"; the channel's `TP1 HIT ... +130 PIPS +2.6R` = a 5.0 stop,
  only plausible at 0.10/pip). **Do not derive it from `formatters.PIP_SIZES`**, which says GOLD 0.01 and would give 0.20. The setting is in price units, like `GOLD_DEFAULT_SL_DISTANCE`.
- **Where the value lives:** new `settings.gold_min_sl_distance = Decimal(os.getenv("GOLD_MIN_SL_DISTANCE", "2.0"))` next to `gold_default_sl_distance` (`settings.py:67-70`),
  and `symbol_policy.get_min_sl_distance(symbol) -> Decimal | None` written like `get_default_sl_distance` (`symbol_policy.py:109-113`): gold aliases -> the setting, other symbols -> `None`
  (no minimum). `.env.example`: add `GOLD_MIN_SL_DISTANCE=2.0` next to `GOLD_MAX_PRICE_DEVIATION` (line 54) with the 20-pip comment. No asset number in `main.py`.
- **Order inside `_use_live_price_for_sizing`:** refusals first and unchanged (non-`Decimal` SL, no live price, market at or beyond the SL: still refused, user decision), then the minimum,
  then the entry replacement. The minimum uses the **post's** entry, so compute it before `entry_price` is overwritten.
- **Moving the SL:** SELL `price + minimum`, BUY `price - minimum`, rounded with `normalize_price(float(...), parsed_signal.symbol)` (`formatters.py:33`; 2 decimals for GOLD/XAUUSD,
  `ROUND_HALF_UP`, returns `float`, so convert back with `Decimal(str(...))`). Assign it to `parsed_signal.stop_loss` before `_handle_parsed_signal`: the MT5 order SL, `signals.stop_loss`
  and `positions.current_sl` then all hold the moved SL. Sizing and the risk guard read entry and SL from the signal, so the lot follows with no other change. TP is not changed.
- **Not covered (user decision):** setups, ladder legs and zone entries keep today's levels. `_fire_next_leg` stays untouched.

## Acceptance Criteria

**Functional Requirements:**
1. For a complete single-message BUY/SELL that passes the live-price check, volume and risk guard are computed with `entry_price` = the live price, not the post's entry.
   Example in Story Context: lot **0.12** (budget 300 / 2,500 per lot), not 0.30; the guard's `order_risk` is called with a 25-point distance and volume 0.12, not 10 points.
2. When the live price equals the post's entry, volume and risk are identical to today (no change for signals posted at market).
3. BUY mirrors SELL: a BUY whose market is above the post's entry gets a smaller lot, not the lot for the post's distance.
4. If the live price is already at or beyond the SL for that direction (SELL: price ≥ SL, BUY: price ≤ SL), nothing is sent or saved: one WARNING names the live price and the SL, followed by
   the existing "Signal rejected" info path of the router. No signal row, no MT5 order call, no `volume_min` fallback order. If the live price cannot be read at that point, the same refusal applies.
5. One INFO log line when a single signal is sized on a different price than the post's: both numbers, e.g. `Single signal chat=… message_id=…: sized on live price 4135 (post entry 4150), SL distance 25`.
   No line when they are equal.

12. Minimum stop for complete single-message signals: minimum = `min(symbol_policy.get_min_sl_distance(symbol), |post entry - post SL|)`. When the live distance `|price - SL|` is below it, the SL
    is moved away from the market to `price +/- minimum` (normalized to broker precision) and the lot and risk guard use that distance. Balance 10,000, 3 %, tick 0.01 = $1:
    - SELL 4150 / SL 4160 / TP 4130, market **4158.5** (1.5 left) -> SL **4160.5**, lot **1.50** (sized on 2.0). BUY mirror: BUY 4150 / SL 4140, market 4141.5 -> SL **4139.5**, lot 1.50.
    - Author's tighter stop: SELL 4150 / SL **4151.5** (15 pips) / TP 4130, market 4150 -> minimum 1.5, nothing moved, lot **2.00**; market **4150.8** (0.7 left) -> SL **4152.3**, lot 2.00.
13. At or above the minimum nothing moves: market 4158 (exactly 2.0 left) -> SL 4160, lot 1.50; market 4135 -> SL 4160, lot 0.12 (AC 1 unchanged).
14. One INFO line when the SL is moved: post SL, new SL and the minimum used, e.g. `... SL moved 4160 -> 4160.5 (minimum 2.0 from market 4158.5)`. No line when it is not moved.
15. A symbol without a policy minimum (`get_min_sl_distance` -> `None`) gets no minimum (20.7 behaviour).
16. The value is a setting (`GOLD_MIN_SL_DISTANCE`, default 2.0 = 20 pips) read through `symbol_policy`, documented in `.env.example`. No asset-specific number in `main.py`.
17. AC 4 refusals keep their priority: market at or beyond the SL is still refused, never widened.

**Integration Requirements:**
6. A complete single-message signal at market still fires instantly, with the same SL, TP, order type and execution path as before (the project's guard rail for this style).
7. Setups and zone legs behave exactly as today: `_fire_next_leg` and its tests are not edited. A BUY/SELL that goes to `_start_setup` (missing SL/TP, multi-TP, SL range, candle-close SL)
   keeps the author's entry as its zone: only the complete-signal branch replaces the entry.
8. `_validate_live_price` is not edited (same `bool` result, same rejection rules: symbol not enabled, MT5 not connected, no market price, no policy, deviation > `GOLD_MAX_PRICE_DEVIATION`).
   `position_sizer.py`, `risk_guard.py` and `position_manager.py` are not edited. Existing tests pass without edits, except fixture-only changes (Story Context).

**Quality Requirements:**

10. Full `pytest` stays green (baseline: 745 passed, 6 skipped on 2026-10-13; 758 after the first implementation and QA; record the exact count).

## Technical Notes
- **Why fix the sizing, not tighten the deviation:** with sizing on the live price the loss at SL is the 3 % budget at any gap, so the money bug is closed without changing which signals trade.
  A wide gap still hurts reward/risk (SELL 4150, market 4135, TP 4130: TP is 5 points away, SL 25), and that is a trading-policy choice for the user, not a bug.
- **Tight stops (decided 2026-10-15, AC 12-17):** larger lots are accepted, but never on a stop under 20 pips from the market unless the author's own stop is tighter. At or beyond the SL: refused.
  Single signals only; setups/zones decided separately later if needed.
- **Still open for the user (not in this story):** keep `GOLD_MAX_PRICE_DEVIATION=100`, lower it (e.g. 15 points), or cap the gap relative to the SL distance (e.g. market may not be past the post's entry by more than half of `|entry − SL|`).
  The minimum stop covers the side of the gap toward the SL; this open decision is about the side toward the TP (reward/risk).
  Any lower value changes which of the channel's signals are skipped. Evidence to decide with: `logs/raise/app.log` lines `Live price check for … entry X vs market Y`. If chosen, it is a one-value change in `.env`
  or a small follow-up story in `symbol_policy`; this story stays valid either way.
- **Residual:** half-spread plus slippage between mid and fill (about 0.1-0.3 points on gold). On a 3-point stop that is a few percent of the budget. Not fixed here; revisit with step 2 (spread filter) or when `open_market_order` can size from its own tick.
- **Floor at `volume_min`:** when the budget is smaller than the minimum lot for the (now longer) SL distance, `leg_volume` returns `volume_min` and the risk can exceed 3 % (logged WARNING, existing behaviour).
  A wider live distance makes that more likely on small balances.
- **Out of scope:** `_validate_live_price` rules, spread filter (roadmap step 2), TP-side check (MT5 already rejects a TP on the wrong side of the market), setups/zones, `main.py` refactor (stories 19.4+ move this code afterwards).
- **Key constraints:** high-risk rule (CLAUDE.md): narrow, observable change in the order path. Complete single-message signals must never break (project memory), so AC 2 and 6 are tested on the base commit too.

## Risk and Compatibility Check
- **Primary risk:** a regression in the instant path: a valid at-market signal not firing or firing with another lot. Mitigation: AC 2/6 tests on base and after; only `entry_price` (a sizing input) changes, not SL, TP or order type; manual demo check.
- **Secondary risk:** the SL-side refusal (AC 4) blocks a signal the old code would have sent. Such an order already fails at MT5 (stops on the wrong side of the market), so the visible change is a clearer rejection reason, not a lost trade.
- **Third:** the signal row now holds the live price, not the post's entry (as for setups). Anything that compares `signals.entry_price` with the post's text would differ. Checked 2026-10-15: readers are the dashboard line, `_handle_correlated_message` (`position.open_price` first, `signal.entry_price` only as fallback), the parsers' own validation (they run before the router, on the parsed value) and the dead risk modules.
- **Fourth:** a fail-closed second price read can refuse a signal that the first read accepted (price feed hiccup in a few ms). Rare, and a skipped trade is the safe side; the WARNING says why.
- **Fifth (v0.4):** a moved SL sits beyond the author's invalidation level (by the minimum minus what was left), so a trade the author would call stopped can still be open. Accepted by the
  user as the price of not trading 0.5-2 point stops; the loss at SL stays at the 3 % budget because the lot is sized on the moved distance. The INFO line (AC 14) makes every move visible.
- **Sixth (v0.4):** the pip unit. Using `PIP_SIZES` (0.01) instead of 0.10 would make the minimum 0.20 and leave the problem in place. The AC 12 numbers (lot 1.50 at 4158.5) catch that mistake.
- **Rollback:** `git revert` the story commit. The new setting has a default; nothing to undo in `.env`.
