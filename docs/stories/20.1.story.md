## Story
**As a** trader running the signal bot,
**I want** a new complete signal such as `JE VENDS GOLD 4150 SL 4160 TP 4130` to always be traded, even when the same chat posted a trade a few minutes earlier,
**so that** a valid signal is never silently treated as a follow-up of an old position and dropped.

## Story Context

**Existing System Integration:**
- Integrates with: `src/correlation_engine/time_matcher.py` (`TimeMatcher.find_matches`, private `_looks_like_new_trade`),
  `src/correlation_engine/setup_aggregator.py` (`looks_like_new_trade`, the rule the router already uses)
- Technology: Python 3.12, re, pytest
- Follows pattern: "Asset-specific values ONLY in `symbol_policy.py`" (`setup_aggregator.looks_like_new_trade` builds its symbol
  list from `symbol_policy.get_enabled_aliases()`); one rule, one place.
- Touch points: `time_matcher.py` lines 98 and 455-460 only. `main.py` unchanged.

**The bug (measured 2026-10-11 with the real `TimeMatcher` and `RegexParser`, one open SELL 3 min old in the same chat):**

| Text | Regex parses | Router rule `looks_like_new_trade` | Time matcher before fix |
|------|:-----------:|:----------------------------------:|:-----------------------:|
| `JE VENDS GOLD 4150 SL 4160 TP 4130` | SELL | yes | correlated at 0.94, **not executed** |
| `J'ACHÈTE GOLD 4150 SL 4140 TP 4170` | BUY | yes | correlated at 0.94, **not executed** |
| `SELL GOLD 4150 SL 4160 TP 4130` | SELL | yes | no match, executed |

Cause: the router correlates before it parses (`main.py:336-362`). The time matcher's own guard only knows
`buy|sell|achat|vente|long|short`, not `vends|vendre|achète|acheter`, which the regex parser trades.
`setup_aggregator._ACTION_WORD` already knows all of them.

## Technical Notes
- **Integration approach:** delete the duplicate rule, call the existing one. No new code path, no new setting.
  `looks_like_new_trade` needs an action word, an enabled symbol alias and a 4-digit price (`_PRICE`); the old private rule accepted 3-5 digits.
  Gold is 4 digits; accept the difference, and note it for future symbols (price digits belong in `symbol_policy`).
- **Known limitation, unchanged:** a follow-up that contains an action word, the symbol and a price
  (`je garde mon sell gold, SL 4170`) is treated as a new trade by both the old and the new rule, so it is not time-matched.
  The router then parses it (regex `SELL … SL`) like any other message. Out of scope.
- **Known limitation, unchanged:** a new signal posted as a Telegram reply goes through reply correlation first. Rare; revisit in step 13.
- **Testing:** pytest with `asyncio_mode = auto` and `--strict-markers` (`pytest.ini`): mark tests `@pytest.mark.unit`; `filterwarnings = error`,
  so no un-awaited coroutines or warnings. Stub repos need `SignalRepo.get_recent_signals(minutes, status=None)` and `get_by_id(id)`,
  `PositionRepo.get_positions_by_signal(id)`; signal and message timestamps are naive UTC (`datetime.now(UTC).replace(tzinfo=None)`).
  Reuse the `TimeMatcher(signal_repo, position_repo)` fixture at `tests/unit/test_correlator.py:468` where it fits.
- **Key constraints:** high-risk code rule (CLAUDE.md): narrow, observable change in correlation only. No change in `main.py`, MT5 or the database.
- **Out of scope:** parse-before-correlate reordering in the router (story 19.8), other review findings (F19, F21, ...), threshold tuning.

## Risk and Compatibility Check
- **Primary risk:** a real follow-up is now classified as a new trade (it contains `sell|buy|vends…` + `gold` + 4-digit price) and is no longer time-matched.
  Before this story it was already skipped when it used English words; this extends the same rule to French words.
- **Mitigation:** such a message still goes to the parser and, for SL/TP restatements, to the setup/zone follow-up handlers that run before correlation in the router (`main.py:290-333`).
- **Rollback:** `git revert` the story commit; no data or config changes.
