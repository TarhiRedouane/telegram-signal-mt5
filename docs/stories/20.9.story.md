## Story
**As a** trader whose bot manages open legs (break-even at TP1, candle-close invalidation, further ladder legs),
**I want** an order that MT5 has filled to stay under the bot's management even if a database write fails at that moment,
**so that** a transient SQLite error (locked file, disk hiccup) never leaves a live position without break-even, and never kills a setup's watcher after MT5 has already accepted an SL move.

## Story Context

**Existing System Integration:**
- Integrates with: `main.py` `ApplicationManager`:
  - `_execute_signal_on_mt5` 1482-1604: one `try` from the signal lookup to the return. The order is sent at 1540; after a fill it creates the position row (1570-1590,
    `_position_repository.create(...)`), marks the signal EXECUTED (1592-1596), returns the position (1601). `except Exception` at 1602-1604 logs and returns `None`.
  - `_fire_next_leg` 1187-1192: `position is None` → `_disarm_or_drop(setup, "order not filled")`; otherwise the position joins `setup.positions` (break-even, invalidation, more legs).
  - `_handle_parsed_signal` (single signals): `position is None` → dashboard "NOT FILLED" (1466).
  - `_apply_position_levels` 566-600: MT5 modify first, then `_position_repository.update_position_mt5_data(position.id, ...)` at 595-596 with no `try`.
    Callers: `_track_setup_legs` (break-even, 1248) and `_apply_setup_levels` (917-930, SL/TP follow-ups pushed to every leg); both gain from the fix.
- `src/database/repository.py`: `BaseRepository.create` (206-220) raises `RepositoryError` on any SQLAlchemy error; `update_position_mt5_data` (536-544) logs and **re-raises** any exception;
  `update` (234-248) does `session.get(Position, record_id)`.
- Technology: Python 3.12 asyncio, SQLAlchemy 2.0 async + aiosqlite, pytest (`filterwarnings = error` in `pytest.ini`).
- Follows pattern: 20.2's rule that trade management continues while something is retried or failed (`be_pending`, `_record_retry_failure`), and the high-risk rule "log every decision".
- Touch points: `_execute_signal_on_mt5` (post-fill part only) and `_apply_position_levels` (DB part only). No change to `repository.py`, `position_manager.py`, setups or the router.

**The bugs (from the code):**
1. **F37, fill then DB error → "not filled".** `open_market_order` succeeded, then `create` or `update_signal_status` raises → the shared `except` returns `None`. In `_fire_next_leg` the
   setup takes "order not filled": a setup without earlier legs is dropped, a setup with legs is disarmed and the new leg is never appended. The MT5 position stays open with its SL/TP
   but gets **no break-even at TP1, no candle-close invalidation, no further legs**. A single signal shows "NOT FILLED" on the dashboard although it filled.
   Same outcome when `_position_repository` is `None` (position stays `None`, 1570).
2. **DB error after an accepted SL move kills the watcher (found while drafting, same family).** `_apply_position_levels` writes the DB after MT5 accepted the modify. If
   `update_position_mt5_data` raises, the exception leaves `_apply_position_levels` → `_track_setup_legs` (break-even loop, 1248) → `_watch_setup`'s catch-all (1084) drops the setup as
   "watcher error". The break-even already applied stays in MT5, but the remaining legs lose management (further break-even retries, invalidation close, idle handling).

**Facts that shape the design (check in code before starting):**
- **Only the part after a successful fill changes.** Everything before the order (lookup, claim, sizing, risk guard) and the rejected-order path keep returning `None`: no order exists, so
  "not filled" is true there.
- **Unsaved position:** when `create` fails or there is no repository, build the same `Position(**kwargs)` that `create` would have stored (the model takes the same keyword arguments,
  `repository.py:209`), unsaved, `id` `None`. Callers use only `mt5_ticket`, `open_price`, `volume`, `current_sl`/`current_tp` and `id` (`grep` in `main.py`: `position.id` is read only at
  596 and in `_handle_correlated_message` 472, which gets positions from the DB). Build the kwargs once and use them for both `create` and the fallback.
- **Signal status:** if `update_signal_status(EXECUTED)` fails after the fill, log ERROR and still return the position. The signal stays in its claimed state, which already blocks a second order.
- **`_apply_position_levels` with an unsaved position:** skip the DB write when `position.id is None`. Do **not** call `update_position_mt5_data(None, …)`: `session.get(Position, None)`
  emits an SQLAlchemy warning, which `pytest.ini` turns into an error (and a future SQLAlchemy may raise).
- **`_apply_position_levels` with a DB error:** catch around the DB write only, log ERROR with the ticket and the levels, return `True`. The return value means "levels are in force in MT5",
  which is what break-even and invalidation decide on.
- **Logging (high-risk rule):** each fallback logs one ERROR naming the ticket and what was not saved, e.g.
  `Ticket 99 filled but its position was not saved (<error>); tracking it in memory, DB row missing`.

## Acceptance Criteria

**Functional Requirements:**
1. After a successful fill, `_execute_signal_on_mt5` returns a position for the ticket in every case: position row saved, `create` raising, or `_position_repository` being `None`.
   In the last two cases the position is an unsaved `Position` with the fill's ticket, open price, volume, SL and TP, and one ERROR is logged with the ticket.
2. A failed `update_signal_status(EXECUTED)` after the fill logs one ERROR and does not change the return value.
3. Setup leg whose position row fails to save: `_fire_next_leg` appends the position, returns True, and the setup is neither dropped nor disarmed by "order not filled"; break-even at TP1 then moves
   that leg like any other (its `open_price` is the fill price).
4. Single signal whose position row fails to save: the dashboard entry is "NEW" with the ticket, not "NOT FILLED".
5. `_apply_position_levels`: when MT5 accepts the modify and the DB write raises, it logs one ERROR and returns True; when `position.id is None` it makes no DB call and returns True.
6. A break-even whose DB write fails completes (`be_done` set once MT5 accepted every leg) and the setup watcher keeps running.

**Integration Requirements:**
7. Unchanged: no order sent → `None` (lookup failure, claim lost, risk guard refusal, order rejected by MT5 with REJECTED status as today). A filled order with a healthy DB behaves exactly as today.
8. `repository.py`, `position_manager.py`, `_fire_next_leg`, `_track_setup_legs` and the router are not edited. Existing tests pass without edits.

## Technical Notes
- **Why an unsaved model, not a dict or `SimpleNamespace`:** the setup code and `_apply_position_levels` treat positions as `Position` objects. An unsaved `Position` with the same fields is
  the smallest thing that behaves the same everywhere; `id is None` is the one marker callers need.
- **What stays lost:** an unsaved position has no DB row, so it is not in `signals`/`positions` history and a restart forgets it (roadmap step 3 persists state; step 6 syncs from MT5).
  The ERROR log names the ticket so it can be found in MT5. This story keeps the running bot managing the trade; it does not repair the DB.
- **Why `True` from `_apply_position_levels` on a DB error:** break-even and invalidation decide on whether MT5 holds the new SL. Returning False would retry an SL move that MT5 already
  accepted (harmless with `NO_CHANGES`, 20.2) but would also keep `be_pending` on and log break-even failures that did not happen.
- **Out of scope:** retrying the failed DB write; repository changes; the poller (20.8); positions never marked closed (F25, step 6).
- **Key constraints:** high-risk rule (CLAUDE.md): narrow, observable change in the order path; every fallback logged at ERROR with the ticket. Complete single-message signals and multi-message
  setups must keep working (AC 7, regression tests).

## Risk and Compatibility Check
- **Primary risk:** turning a real "not filled" into "filled", which would make a setup track a ticket that does not exist. Mitigation: the fallback is reached only after `order_result.success`
  is True; every pre-fill failure keeps returning `None` (AC 7 regression tests).
- **Secondary risk:** a position with `id is None` reaching code that needs a DB id. Mitigation: the only live reader of `position.id` with such positions is `_apply_position_levels`, which skips
  the write (AC 5). `_handle_correlated_message` loads positions from the DB, so it never sees an unsaved one.
- **Rollback:** `git revert` the story commit. No DB or setting change.
