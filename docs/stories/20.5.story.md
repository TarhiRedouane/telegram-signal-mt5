## Story
**As a** trader running the signal bot,
**I want** the bot to reconnect to MT5 by itself when the terminal was not ready at startup, and to stop listing every broker symbol on each call,
**so that** a late-starting terminal does not freeze every price check for 60 s until I restart, and the 5 s setup/zone polls stay light.

**The bugs (from the code):**
1. F23. `_initialize_pool` sets `self._initialized = True` (421) even when `session.connect(...)` returned `False` (418-419). The queue stays empty.
   From then on `get_connection` passes both checks, then waits `timeout_seconds` (60 s) on `connection_queue.get()` and raises
   `RuntimeError("Timeout waiting for MT5 connection ...")`. Every price check and every watcher poll stalls 60 s. Only a restart fixes it,
   because `_ensure_initialized` returns immediately once `_initialized` is True.
2. Setting `_initialized` back to `False` is not enough: `_ensure_initialized` keeps `self._initialization_task` (448), a finished task,
   and awaits it again without re-running `_initialize_pool`. The task must be cleared on failure.
3. `main.py:1654` logs "MT5 runtime initialized" after `_ensure_initialized()` returns, even when MT5 did not connect.
4. F28. `_resolve_broker_symbol_name` calls `mt5.symbols_get()` (a blocking call returning thousands of objects, inside the event loop)
   for every candidate on every price, candle and order call: every 5 s per setup, twice per zone poll, plus each order.

**Facts that shape the design (check in code before starting):**
- `get_connection` already raises `RuntimeError("Connection pool initialization failed")` when `_initialized` is False (466-467). That is the
  fast failure we want. `get_current_price` catches it and returns `None` (998-1000). Check that the order path, `get_closed_rates` and
  `main.py` callers handle `RuntimeError` the way they handle the 60 s timeout today (same exception type, so they should).
- `mt5.initialize` can take several seconds (it may launch the terminal). Retrying on every 5 s poll would make each poll block. Throttle with
  `reconnect_delay`: after a failed attempt, do not retry until that many seconds have passed.
- The broker symbol list does not change during a session. A cached name stays valid until the session is rebuilt (reconnect).
- Do not cache the fallback result when the lookup itself failed (`symbols_get()` returned empty/`None` or raised): the terminal may just
  not have loaded its symbols yet.

## Acceptance Criteria

**Functional Requirements:**
1. When `session.connect(...)` returns `False` (or `_initialize_pool` raises), `_initialized` stays `False` and `_initialization_task` is reset
   to `None`, so the next `_ensure_initialized()` runs `_initialize_pool` again.
2. Retries are throttled with backoff: after a failed attempt, `_ensure_initialized()` does not call `connect` again until a delay has
   passed (monotonic clock). The delay starts at `reconnect_delay` and doubles per consecutive failure, capped at 60 s (same cap as
   `_reconnect_connection`); it resets on success. The check runs inside `_initialization_lock`, after the `_initialized` double-check, so
   concurrent callers share one attempt. In the window `get_connection` fails fast with `RuntimeError("Connection pool initialization failed")`
   (no 60 s wait). Why the backoff: `connect` also fails for config errors (empty `MT5_PATH`, terminal on another account, wrong account mode;
   connection.py:171-251), which would otherwise log an ERROR and call `mt5.initialize`/`shutdown` every 5 s forever.
3. When a retry succeeds, the pool fills as today and all later calls work without a restart. Log one INFO line on recovery
   ("MT5 connection established after N failed attempts") and one WARNING per failed attempt (not per call inside the throttle window).
4. `main.py` `_initialize_mt5_connection` logs "MT5 runtime initialized" only when the pool is initialized; otherwise it logs a WARNING that
   MT5 is not reachable yet and that it will retry on use. Startup is not blocked and does not crash (degraded mode as today).
5. `_resolve_broker_symbol_name` keeps a per-instance cache `{candidate: resolved_name}`. A hit returns the cached name with no
   `symbols_get()` call. The cache is filled only when `symbols_get()` returned a non-empty list (a match, or no match falling back to the
   candidate); it is not filled when the list is empty/`None` or the call raised.
6. The cache is cleared when the session is rebuilt (successful `_reconnect_connection` and a successful retry in AC 3).

**Integration Requirements:**
7. Resolution order and results are unchanged (exact, case-insensitive, normalized); only repeated lookups are skipped.
8. No change to order requests, retry/circuit-breaker decorators, `get_connection` semantics when the pool is healthy, settings, parsing or the DB.
9. `position_manager.py` is not edited: it already calls `connection_manager._resolve_broker_symbol_name` and gets the cache for free.

**Quality Requirements:**
10. New tests fail on the base commit (record in Dev Agent Record). Cases in Task 1.
11. Full `pytest` stays green (baseline: 724 passed, 6 skipped per 20.4).
12. `black --check`, `ruff check` clean on touched files; `mypy src/`: no new errors versus baseline (227 errors in 33 files, per 20.4). Record before/after.

## Technical Notes
- **Why throttle instead of retrying on every call:** `connect` may launch or wait for the terminal. Without a window, each 5 s poll
  would block inside it, which is the same stall in a different place.
- **Why a plain dict, not `lru_cache`:** the cache must be per manager instance and clearable on reconnect. A dict is two lines.
- **Order path:** `open_market_order` is wrapped in `@retry_on_failure(max_attempts=3, delay=1.0, backoff=2.0)` (position_manager.py:296).
  With MT5 down it used to wait up to 3 x 60 s; now each attempt fails fast, so the signal fails in about 3 s with the error logged.
  No change needed there, but expect that behaviour.
- **`connect` is sync MT5 IPC inside the event loop** (`mt5.initialize`): pre-existing, not fixed here. The backoff limits how often it can stall.
- **Why not a background reconnect task:** a retry on use is enough for the live paths (watchers and orders call MT5 often) and adds no
  new task to cancel at shutdown. A watchdog can join the restart-state work (roadmap step 3) if ever needed.
- **`symbols_get()` still blocks the loop** on a miss (first lookup per candidate). Moving it to a thread is a separate change; the cache
  removes the repeat cost, which is the finding.
- **Out of scope:** reconnect backoff inside `_reconnect_connection`, circuit-breaker tuning, filling mode and magic number (F29), `cli.py stop`
  PID check (20.6), per-chat ordering (F24).
- **Key constraints:** high-risk rule (CLAUDE.md): narrow, observable change. Never log credentials; the new log lines carry attempt counts only.

## Risk and Compatibility Check
- **Primary risk:** a retry path that leaves the pool half built (queue filled twice, or two concurrent attempts), which would let more
  callers than `max_connections` use the one session. Mitigation: attempts only run under `_initialization_lock`, the queue is filled only in the
  success branch, tests for fail → retry → succeed, and a check that the queue size equals `max_connections` after recovery.
- **Secondary risk:** a stale cached symbol name after the broker changes its symbol list. Mitigation: cache cleared on reconnect; names do
  not change within a session.
- **Rollback:** `git revert` the story commit. No DB or setting change to undo.

### Code Quality Assessment
Narrow change in the right place. The root cause (F23) is fixed where every caller routes through (`_ensure_initialized` /
`_initialize_pool`), not per caller. The pool queue is filled only on the success branch, so a retry cannot double-fill it (test asserts
`qsize() == max_connections`). The stale-task trap the PO flagged is handled with `finally`. The throttle check sits inside the lock after
the double-check, so concurrent callers share one attempt (tested). `_note_init_failure` runs on both the `False` and the exception path,
so a raising connect is throttled too.

Cancellation: if the caller awaiting `_initialize_pool` is cancelled, `CancelledError` (a `BaseException`) skips `_note_init_failure`, so
the next call retries without waiting. Acceptable: no partial state (the queue fill has no real suspension point) and the `finally` still
clears the task.

Symbol cache (F28): match order unchanged; the rewrite with `next(...)` is shorter than the three loops and equivalent (exact match implies
`str`). The listing stays inside the `try`, which keeps the old tolerance for odd `symbols_get()` returns (the dev caught this through two
existing tests). Caching an unmatched candidate as itself is correct: the broker list is fixed for a session, and it is cleared on reconnect.
