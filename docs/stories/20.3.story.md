## Story
**As a** trader running the signal bot with several Telegram channels,
**I want** a signal in channel B to be stored, executed and correlated independently of signals from channel A,
**so that** two channels that reach the same Telegram message id never skip, overwrite or steer each other's trades.

## Story Context

**Existing System Integration:**
- Integrates with: `src/database/models.py` `Signal` (lines 125-128: `telegram_message_id` `unique=True`, `telegram_chat_id` indexed);
  `src/database/repository.py` `save_signal` (288-316) and `find_by_message_id` (318-324); `src/correlation_engine/correlator.py`
  `get_position_by_message_id` (338-365), `get_signal_by_message_id` (407-421), reply lookup at line 205; `main.py` edit check (~324)
  and execution claim (~1442); `main.py` synthetic zone ids `-(message_id * 10 + index)` (~747); `DatabaseManager.initialize`
  (`repository.py` ~73-104, where `create_all` builds the schema).
- Technology: Python 3.12, SQLAlchemy 2 async + aiosqlite, pytest (`asyncio_mode=auto`, `-W error`).
- Follows pattern: "Repository pattern only" (`repository.py` is the sole DB access point); "log every decision"; high-risk rule
  (Telegram + MT5 path: narrow, observable change).
- Touch points: `models.py` (constraint), `repository.py` (lookups take chat id), `correlator.py` (pass chat id through),
  `main.py` (pass chat id at the two call sites, zone-id comment), one idempotent index upgrade at startup, one data backup step.
  No change to MT5 calls, scoring, parsing, or break-even/close logic.

**The bug (from the code):**
1. `Signal.telegram_message_id` is unique across all chats. Message ids are per chat, so channel A and channel B reach the same ids.
2. `save_signal` looks up by message id alone. If A once stored message N, a complete signal N from B returns A's row. Execution then
   fails to claim it (A's row is EXECUTED), logs "already claimed or processed", and **B's trade is silently skipped**.
3. The reply-chain lookup in the correlator can resolve root N in B's chat, then find **A's signal N** and A's position. LLM context
   analysis could then change SL/TP on the wrong position.
4. Synthetic zone ids can collide across chats the same way.
5. Likelihood grows with each channel (roadmap step 18) and with time, because the DB keeps every past id.

**Measured facts that shape the design (re-checked 2026-10-12 against code and the live DB):**
- Live DB is **per broker instance**: `data/<BOT_INSTANCE>/signal_ea.db` (`database/__init__.py` `get_database_url`). With
  `BOT_INSTANCE=raise` that is `data/raise/signal_ea.db`. `data/signal_ea.db` is a stale pre-instance file (last write September);
  it is not the live DB.
- Alembic never runs in production: `main.py:246` calls `initialize_database(run_migrations=False)`. The schema comes only from
  `create_all` in `DatabaseManager.initialize`. No `migrations/versions/` directory exists and the live DB has no `alembic_version` table.
- `src/database/migrations/env.py` cannot run as wired: it ignores the URL passed by `run_database_migrations` (falls back to
  `data/signal_ea.db`, wrong for an instance), calls `asyncio.run` from inside the running loop, and executes raw-string PRAGMAs
  (SQLAlchemy 2 rejects them). Reviving Alembic is a separate piece of work, not this fix.
- The old unique is a plain index, not a table constraint: `CREATE UNIQUE INDEX ix_signals_telegram_message_id ON signals (telegram_message_id)`.
  The fix is index-only: drop it, recreate it non-unique, add a unique index on `(telegram_chat_id, telegram_message_id)`. No table
  rebuild; rows, `signals.id` values and foreign keys are untouched.
- `create_all` does not add indexes to a table that already exists, so an existing DB needs an explicit upgrade step.
- Live `raise` DB at backup: 18 signals, 12 positions, no duplicate `telegram_message_id`, integrity ok. The new unique index cannot fail on it.
- `save_signal` already has an idempotency path (returns existing id on duplicate). That path must match on `(chat, message)` too, or
  it reintroduces the bug.

## Acceptance Criteria

**Functional Requirements:**
1. The `signals` table has a unique constraint on `(telegram_chat_id, telegram_message_id)`. The single-column unique on
   `telegram_message_id` is removed. A non-unique index on `telegram_message_id` alone stays (reply-chain lookups use it).
2. `SignalRepository.save_signal` treats a signal as duplicate only when both chat id and message id match. A message N from chat B
   with an existing row for message N from chat A is **inserted**, not returned as A's row.
3. Every signal lookup takes the chat id: `find_by_message_id(message_id, chat_id)` (signature change, no default). Call sites in
   `repository.py`, `correlator.py` (`get_position_by_message_id`, `get_signal_by_message_id`, reply-chain at line 205), and `main.py`
   (~324 edit check, ~1442 execution claim) pass the chat id of the message being handled.
4. Reply-chain lookup: the root message id from the reply tracer is resolved **in the chat of the replying message**. A reply in chat B to
   message N never returns a position or signal from chat A.
5. Synthetic zone ids (`main.py` ~747) cannot collide across chats: they are stored with the zone's chat id, and the key is now
   `(chat, message)`. No id change needed; the comment that says the id is globally unique is corrected.
6. The schema upgrade preserves all existing rows and foreign keys (positions reference `signals.id`). `signals.id` values do not change.
7. The upgrade runs at startup in `DatabaseManager.initialize`, after `create_all`, inside one transaction, and is idempotent (a second
   start, or a fresh DB, changes nothing). Rollback is restoring the backup; no downgrade code.
8. Startup logs one line when the upgrade is applied (`signals: message id unique per chat (index upgraded)`); nothing when already done.

**Integration Requirements:**
9. No change to scoring, thresholds, parsing, risk manager, break-even/close, MT5 calls, or the circuit breaker wiring.
10. Behaviour for a single channel is unchanged: same log decisions and same MT5 calls on a replayed single-channel message set.
11. New unit tests use a repository on an in-memory DB built the same way as production (`DatabaseManager.initialize`). One test builds the
    old schema (global unique index) and checks the upgrade converts it and keeps the rows.
12. Full `pytest` stays green (baseline per story 20.2: 711 passed, 6 skipped).

**Quality Requirements:**
13. New tests fail on the base commit (record in Dev Agent Record). Required cases in Task 1.
14. `black --check`, `ruff check` clean on touched files. `mypy src/`: no new errors versus baseline (227 errors in 33 files, per 20.2). Record before/after.
15. Dev Agent Record lists: backup file name and checksum, upgrade run on a copy of the live DB (indexes and row counts before/after), tests added, failing-before / passing-after output, full pytest result.

## Technical Notes
- **Why not keep the single-column unique and add a second key:** the unique on `telegram_message_id` is the root of F19. Any remaining global unique
  keeps the cross-channel collision. The per-chat unique is the minimum change.
- **Live upgrade happens on the user's next bot start:** the dev never runs it against `data/raise/signal_ea.db`; only on a copy.
  Each broker instance upgrades its own DB on its own first start.
- **Why not Alembic:** it is not wired in production and its `env.py` cannot run (see measured facts). The change is three index statements;
  an idempotent step next to `create_all` is where the schema is actually managed today. If Alembic is revived later, its baseline is the
  post-20.3 schema.
- **Rollback:** restore the backup. Old code on an upgraded DB still runs (the composite unique is stricter only across chats), but once two
  channels store the same message id the old global unique cannot be recreated.
- **Out of scope:** storing pending state across restarts (roadmap step 3); fill price (20.4); MT5 startup (20.5); PID check (20.6);
  per-chat ordering of processing (F24, story 19.8); positions never marked closed (F25, step 6).
- **Key constraints:** high-risk code rule (CLAUDE.md): narrow change, log every decision. Secrets: do not log raw chat ids beyond what current logs already show.

## Risk and Compatibility Check
- **Primary risk:** a missed `find_by_message_id` call still passes one argument, or a caller passes the wrong chat id, and a signal is still
  matched across chats. Mitigation: required keyword argument (AC 3), grep check in Task 3, Task 1 tests for both directions.
- **Secondary risk:** the startup upgrade fails half-way on live data. Mitigation: index-only change in one transaction (SQLite DDL is
  transactional), backup (Task 2), copy-based run (Task 6), integrity and FK checks.
- **Rollback:** restore the Task 2 backup and `git revert` the story commit.
